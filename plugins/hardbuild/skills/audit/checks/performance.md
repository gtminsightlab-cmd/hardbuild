# Performance audit — checks

**Purpose:** Find where your app can be made faster for users — real Core Web Vitals, the JS the browser must download before it can do anything, and the server-side waits (waterfalls, unindexed queries, no caching) that make every page feel slow.
**Scorecard row:** Performance · **Report:** `audits/performance.md` · **Overlaps:** Database (index coverage, query plans in depth), Mobile & Tablet (image sizing on small screens), Dependencies (heavy packages), Observability (Speed Insights/monitoring setup), Cost (function duration billing). Reference, don't repeat.

## Inputs to gather first
- URL: `.hardbuild.json → audit.productionUrl` (preferred: real CDN + Vercel edge) or `next build && next start` locally. Chrome available? `which google-chrome chromium chromium-browser || ls ~/.cache/ms-playwright 2>/dev/null`.
- Build output: `pnpm build 2>&1 | tee /tmp/build.log` (or npm/yarn) — the route table with `First Load JS` is the single most useful artifact. Next version: `grep '"next"' package.json`.
- Vercel MCP if attached: `get_runtime_logs`, Speed Insights data; project `functions` config in `vercel.json` / `next.config.*`.
- Supabase MCP if attached: `get_advisors(type: performance)`, `pg_stat_statements`.

## Checks
Format: `ID · weight · check · how to verify (strongest first) · typical failure`

- **PRF-01 · 3 · Core Web Vitals pass on the main routes (LCP <2.5s, INP <200ms, CLS <0.1).**
  VERIFY: `npx lighthouse <url> --only-categories=performance --quiet --chrome-flags="--headless" --output=json --output-path=/tmp/lh-home.json && node -e "const r=require('/tmp/lh-home.json');console.log(r.categories.performance.score*100, r.audits['largest-contentful-paint'].displayValue, r.audits['cumulative-layout-shift'].displayValue, r.audits['total-blocking-time'].displayValue)"` on `/`, the signed-in landing, and the core list (use `--extra-headers` with a session cookie for authed routes). Target perf ≥90 mobile. Else Vercel MCP → Speed Insights p75 for the same routes. Else READ: `grep -rn "@vercel/speed-insights" package.json app/layout.tsx` → presence only is INFERRED, not a pass.
  FAIL PATTERN: perf score 40–60 on mobile; LCP element is a hero image without `priority`; CLS from fonts/images without dimensions; no Speed Insights so nobody knows.
- **PRF-02 · 3 · First Load JS per route under 200 kB.**
  VERIFY: from `/tmp/build.log` read the route table; flag every route with `First Load JS` >200 kB and the shared chunk >100 kB. Deeper: `ANALYZE=true pnpm build` if `@next/bundle-analyzer` is configured (`grep -n "bundle-analyzer" next.config.*`), else `npx @next/bundle-analyzer` is not standalone — add the plugin or inspect `.next/static/chunks` sizes: `du -sk .next/static/chunks/*.js | sort -rn | head`.
  FAIL PATTERN: shared chunk at 350 kB because `recharts`, `date-fns` (whole), `lodash`, or `@supabase/supabase-js` + `framer-motion` are imported in the root layout; a settings page at 600 kB from a rich-text editor loaded eagerly.
- **PRF-03 · 2 · `"use client"` is scoped, not sprinkled.**
  VERIFY: `grep -rln '"use client"' app src --include=*.tsx | wc -l` vs `find app src -name '*.tsx' | wc -l` → >50% client is a smell; `grep -rln '"use client"' app --include=page.tsx --include=layout.tsx` → any `page.tsx`/`layout.tsx` marked client is a finding (it drags the whole subtree to the client). For each client file, READ: does it actually use `useState`/`useEffect`/event handlers/browser APIs? `grep -L "useState\|useEffect\|onClick\|onChange\|useRouter\|window\." $(grep -rln '"use client"' app components --include=*.tsx)` → client components with no client-only API.
  FAIL PATTERN: `"use client"` at the top of a 400-line page because one button needed `onClick`; data fetched with `useEffect` + `supabase-js` in the browser when a server component could pass it as props.
- **PRF-04 · 2 · Heavy libraries are dynamically imported.**
  VERIFY: identify heavy deps in `package.json` (`recharts|chart.js|@tiptap|react-quill|monaco|pdfjs|mapbox|leaflet|three|framer-motion|xlsx|jspdf|@react-pdf`) and `grep -rn "from ['\"]\(recharts\|@tiptap\|...\)" app components --include=*.tsx`; each should be behind `next/dynamic` (`grep -rn "dynamic(" app components --include=*.tsx`) or imported only inside a route that needs it, never in a shared layout. `ssr: false` for browser-only libs (maps, editors).
  FAIL PATTERN: `import { LineChart } from 'recharts'` in `components/dashboard/stats.tsx` imported from the root layout header; PDF generator bundled into every page.
- **PRF-05 · 2 · Images go through `next/image` with correct priority and sizes.**
  VERIFY: `grep -rn "<img" app components --include=*.tsx | wc -l` → 0 (exceptions: SVG logos, email templates — cite them); `grep -rn "<Image" app components --include=*.tsx | grep -c "priority"` → exactly the above-the-fold hero/LCP image per route has `priority`; `fill` without `sizes` (see Mobile MOB-09); `next.config.* images.remotePatterns` includes the Supabase Storage host so Storage images are optimized (`grep -n "remotePatterns\|supabase.co" next.config.*`). Lighthouse audits `uses-responsive-images`, `offscreen-images`, `modern-image-formats` should be empty.
  FAIL PATTERN: raw `<img src={publicUrl}>` from Supabase Storage at 4 MB original size; `unoptimized: true` globally "to fix a deploy error"; every image `priority` (defeats lazy loading).
- **PRF-06 · 2 · Fonts load via `next/font`, no external font CSS.**
  VERIFY: `grep -rn "next/font" app --include=*.tsx -l` → used in root layout with `display: 'swap'` and a `variable`; `grep -rnE "fonts.googleapis.com|fonts.gstatic|@import url\(|<link[^>]*font" app components --include=*.tsx --include=*.css` → must be empty; `curl -s <url> | grep -c "fonts.googleapis"` → 0. ≤2 families, ≤4 weights (`grep -n "weight:" app/layout.tsx`).
  FAIL PATTERN: `<link href="https://fonts.googleapis.com/css2?family=Inter:wght@100..900">` in `<head>` (render-blocking + CLS); font files in `/public` with no `preload`; 3 families × 6 weights.
- **PRF-07 · 3 · No data-fetching waterfalls in server components.**
  VERIFY: `grep -rn -B1 -A1 "await supabase\|await fetch\|await db\." app --include=page.tsx --include=layout.tsx` → two or more independent `await`s in sequence inside one component is a waterfall; they should be `Promise.all([...])` (`grep -rn "Promise.all" app --include=*.tsx | wc -l`). Parent layout fetching user → child page fetching the same user again (`grep -rn "auth.getUser()" app --include=*.tsx | wc -l` — should be deduped via `React.cache()` or passed down). `<Suspense>` boundaries around slow sections (`grep -rn "<Suspense" app --include=*.tsx | wc -l`) so the shell streams.
  FAIL PATTERN: `const user = await getUser(); const org = await getOrg(user.id); const items = await getItems(org.id); const stats = await getStats(org.id);` — 4 round trips to Supabase (~80–300 ms each from Vercel region to Supabase region) before any HTML; no `loading.tsx` so the user stares at the previous page.
- **PRF-08 · 2 · Caching is deliberate: fetch cache, `revalidate`, `unstable_cache`/`"use cache"`.**
  VERIFY: `grep -rnE "export const (revalidate|dynamic|fetchCache)" app --include=*.tsx --include=*.ts` → every route has a conscious choice or inherits one; `grep -rnE "cache: ['\"]no-store['\"]|next: \{ revalidate" app lib --include=*.ts*`; `grep -rn "unstable_cache\|\"use cache\"\|cacheTag\|cacheLife\|revalidateTag" app lib --include=*.ts* | wc -l` → shared reads (plans, settings, reference tables) should be cached and invalidated on write. Note: Supabase client calls are NOT auto-cached by Next — they are plain network calls; wrap with `unstable_cache`/`"use cache"` where safe. Next 15+ defaults to uncached fetch; Next 14 defaults to cached — check version.
  FAIL PATTERN: `export const dynamic = 'force-dynamic'` on every page to "fix stale data"; reference tables re-queried on every request; cached user-specific data leaking across users (cache key missing `userId`) — that one is a Security finding too.
- **PRF-09 · 3 · Supabase query shape: narrow selects, no N+1, paginated.**
  VERIFY: `grep -rnE "\.select\(\s*['\"]\*['\"]?\s*\)|\.select\(\)" app lib components --include=*.ts* | wc -l` → `select('*')` on wide tables is a finding; `grep -rn -A3 "\.map(async\|for (const .* of .*) {" app lib --include=*.ts* | grep "supabase\|\.from(" ` → query inside a loop = N+1 (use a join `select('*, items(*)')` or `.in()`); `grep -rnE "\.from\(['\"][a-z_]+['\"]\)\.select" app lib --include=*.ts* | grep -vE "\.range\(|\.limit\(|\.single\(|\.maybeSingle\(|count" ` → unbounded list queries. Supabase MCP: `get_advisors(type: 'performance')` for unindexed FKs; `select query, calls, mean_exec_time from pg_stat_statements order by mean_exec_time desc limit 10;` (if extension enabled). Index detail → Database.
  FAIL PATTERN: dashboard loads `select('*')` from `quotes` (40 columns, JSONB payloads) to render 3 numbers; `for (const q of quotes) await supabase.from('clients').select().eq('id', q.client_id)`; list page with no `.range()` that gets slower every week.
- **PRF-10 · 2 · Static/ISR where content allows.**
  VERIFY: in `/tmp/build.log` route table, marketing/docs/pricing/blog routes should be `○ (Static)` or `● (SSG)`/ISR, not `ƒ (Dynamic)`; `grep -rn "generateStaticParams" app --include=*.tsx -l`; `grep -rn "cookies()\|headers()\|searchParams" app/\(marketing\)/** 2>/dev/null` → these force dynamic rendering on pages that should be static. `curl -sI <url>/pricing | grep -i "x-vercel-cache\|cache-control"` → `HIT`/`STALE` and `s-maxage` expected for public pages.
  FAIL PATTERN: landing page `ƒ Dynamic` because the root layout calls `supabase.auth.getUser()` for a nav avatar; every public page `x-vercel-cache: MISS` with `cache-control: private, no-cache`.
- **PRF-11 · 1 · Runtime choices (Edge vs Node) are intentional.**
  VERIFY: `grep -rn "export const runtime" app --include=*.ts* ` → `edge` only for lightweight, latency-sensitive handlers that don't need Node APIs or heavy SDKs; `middleware.ts` kept small (`wc -l middleware.ts`, no DB round-trips beyond the Supabase session refresh); `grep -n "maxDuration\|regions" vercel.json next.config.* app/**/route.ts` → Vercel function region should match the Supabase project region (`get_project` → region) to avoid cross-region hops on every query.
  FAIL PATTERN: Vercel functions in `iad1` with Supabase in `eu-west-1` (~90 ms per query); `runtime = 'edge'` on a route that imports `pdfkit` (fails or balloons); middleware querying `profiles` on every request.
- **PRF-12 · 1 · Third-party scripts load via `next/script` with the right strategy.**
  VERIFY: `grep -rnE "<script[^>]*src=" app components --include=*.tsx` → should be empty; `grep -rn "next/script" app components --include=*.tsx -A3 | grep -o "strategy=\"[a-zA-Z]*\"" | sort | uniq -c` → analytics/chat widgets/pixels on `afterInteractive` or `lazyOnload`, nothing on `beforeInteractive` except consent/anti-flicker. Lighthouse `third-party-summary` total blocking time <250 ms. N/A if no third-party scripts.
  FAIL PATTERN: Intercom/HubSpot chat widget as a raw `<script>` in `<head>` adding 300 kB and 400 ms TBT; GTM loading five pixels before hydration.
- **PRF-13 · 1 · Build is clean: no oversized deps, no dev-only code in prod.**
  VERIFY: `/tmp/build.log` has no `⚠ Warning` about large page data or `Serializing big strings`; `npx depcheck 2>/dev/null | head` or `grep -nE "\"(moment|lodash|rxjs|aws-sdk)\"" package.json` → known-heavy packages with lighter replacements (`date-fns`/`dayjs`, `lodash-es` with named imports); `grep -rn "console.log" app components lib --include=*.ts* | wc -l` → `compiler.removeConsole` in `next.config.*` for prod. Full dep review → Dependencies.
  FAIL PATTERN: `moment` + locales (300 kB) for one date format; `import _ from 'lodash'`; 200 `console.log` statements shipping to users.

## Scoring notes
- PRF-01 (mobile perf score <50 or LCP >4 s on the core route), PRF-02 (any primary route >400 kB First Load), PRF-07 (3+ sequential awaits on the signed-in landing), PRF-09 (N+1 in a loop or unbounded list on a growing table) → CRITICAL; grade cap D. Cached user-specific data without a user key (PRF-08) is CRITICAL and belongs in Security as the primary finding.
- PRF-01 with only Speed Insights *presence* is INFERRED (50) — presence proves monitoring, not speed. A Lighthouse run against a local `next dev` server is INFERRED too (dev mode is slow by design); only `next build && next start` or the production URL counts as VERIFIED.
- PRF-02/10 are VERIFIED when quoted from a real build log; if the build fails, record the failure as a Build/CI finding and mark these UNCHECKED → FAIL.
- One root cause, one finding: a client-marked root layout (PRF-03) is usually the cause of the oversized shared chunk (PRF-02) — file once under PRF-03 and reference it.
- "To raise confidence": `productionUrl` + a headless Chrome for Lighthouse (`npx playwright install chromium` provides one; point Lighthouse at it with `--chrome-flags` or use `CHROME_PATH`); a completed `pnpm build`; Vercel MCP for Speed Insights p75 and function regions; Supabase MCP for `get_advisors` and `pg_stat_statements`; `@next/bundle-analyzer` configured for PRF-02/04.
