# Integrations audit — checks

**Purpose:** Verify third-party integrations are implemented correctly — every external call is keyed from env, server-side, bounded in time, honest about failure, idempotent where money or messages move, and switchable off without a deploy.
**Scorecard row:** Integrations · **Report:** `audits/integrations.md` · **Overlaps:** Security (SEC-01 secrets, SEC-08 webhook signatures — headline there, mechanics here), Error Handling (user-facing failure UX), Cloud Cost (API spend caps), Billing & Tax (Stripe business logic — here only the plumbing), Test Coverage (mocks are listed here, coverage scored there). Reference, don't repeat.

## Inputs to gather first
- SDK inventory: `jq -r '.dependencies | keys[]' package.json | grep -iE "stripe|resend|sendgrid|postmark|twilio|ringcentral|googleapis|@google|openai|@anthropic|@ai-sdk|langchain|hubspot|apollo|zapier|n8n|slack|@sentry|posthog|mixpanel|segment|algolia|mapbox|plaid|docusign|@upstash|@vercel/(kv|blob)|svix|inngest|trigger.dev"`.
- Raw HTTP inventory: `grep -rnoE "fetch\(\s*[\`'\"]https?://[^/\`'\"]+" --include=*.ts --include=*.tsx . | grep -v node_modules | sed -E 's/.*https?:\/\///' | sort | uniq -c | sort -rn` → external hosts hit without an SDK; plus `axios.create\(|ky\.|got\(`.
- Env surface: `cat .env.example` (or `.env.local.example`) and `grep -rhoE "process\.env\.[A-Z0-9_]+" --include=*.ts --include=*.tsx . | sort -u` → the diff between the two is the undocumented set.
- Webhook routes: `git ls-files | grep -iE "webhook|hooks?/.*route\.ts|callback"`.
- Build a table: integration → purpose → files → env vars → inbound webhook? → money/message-sending? Every check below runs per row of this table; score the worst row, list the rest.

## Checks
Format: `ID · weight · check · how to verify (strongest first) · typical failure`

- **INT-01 · 2 · Every integration is inventoried and has an owner file.**
  VERIFY: the Inputs table is complete — each SDK in `package.json` and each external host from the `fetch(` grep maps to one module under `lib/<provider>/` or `lib/integrations/`, not scattered `fetch` calls in components. `grep -rln "api.stripe.com\|api.openai.com\|api.resend.com" --include=*.tsx` → direct provider calls from UI files = FAIL. Dead SDKs (in deps, zero imports: `grep -rln "from 'stripe'" | wc -l`) are a LOW finding (reference Dependencies).
  FAIL PATTERN: Resend called from a server action, a route handler, and an edge function with three different `from:` addresses.
- **INT-02 · 3 · Keys come from env, server-side only, and are validated at boot.**
  VERIFY: `grep -rnE "(sk_|rk_|re_|SG\.|AC[0-9a-f]{32}|sk-ant-|sk-proj-|xoxb-|whsec_)[A-Za-z0-9_-]{8,}" --include=*.ts --include=*.tsx --include=*.json . | grep -v node_modules` → empty (literal keys). Each provider client must be constructed in a file that is a route handler, server action, `import 'server-only'` module, or `supabase/functions/*`; `grep -rn "NEXT_PUBLIC_" .env.example | grep -iE "secret|key|token"` → only truly public keys (Stripe publishable `pk_`, PostHog project key, Google Maps browser key with referrer restriction). Boot validation: a `lib/env.ts` with `zod`/`@t3-oss/env-nextjs` that throws on missing vars, so a misconfigured deploy fails at build rather than on first customer request.
  FAIL PATTERN: `new OpenAI({ apiKey: process.env.NEXT_PUBLIC_OPENAI_KEY })` in a client component "because streaming".
- **INT-03 · 2 · Every outbound call has a timeout.**
  VERIFY: SDK clients constructed with `timeout`/`maxRetries` (Stripe `new Stripe(key, { timeout: 10000, maxNetworkRetries: 2 })`, OpenAI `{ timeout: 60000 }`, Resend/Twilio default to long or none); raw `fetch` wrapped with `AbortSignal.timeout(ms)` or `signal:` — `grep -rn "AbortSignal.timeout\|AbortController" --include=*.ts | wc -l` vs the fetch count from Inputs. Route handlers calling slow providers must set `export const maxDuration` deliberately (and ≤ the plan limit). No timeout on a provider call inside a server action = the user's form hangs for Vercel's full function limit.
  FAIL PATTERN: `await fetch('https://api.hubspot.com/...')` with no signal, inside a `"use server"` action behind a submit button.
- **INT-04 · 2 · Failures are caught and surfaced with a user-visible fallback.**
  VERIFY: each provider call site has a `try/catch` (or `.catch`) that (a) logs with provider name + request id, (b) returns a typed error the UI renders ("We couldn't send your quote email — saved as draft, retry?"), and (c) does not take down unrelated work (an analytics or email failure must not fail the DB write that preceded it). `grep -rn -A3 "await resend\.\|await stripe\.\|await openai\." --include=*.ts | grep -c "catch"` vs call count. Also confirm the DB write and the external call are ordered so a provider failure cannot leave a half-state (write first, then notify; or outbox pattern).
  FAIL PATTERN: `await supabase.from('orders').insert(...); await sendConfirmation()` — email fails, the action throws, the UI says "something went wrong", the order exists.
- **INT-05 · 3 · Retries are bounded and writes are idempotent.**
  VERIFY: Stripe: every `paymentIntents.create`/`checkout.sessions.create`/`invoices.create` passes `{ idempotencyKey }` derived from the app's own id (`grep -rn "idempotencyKey" --include=*.ts`); email/SMS sends record a `sent_at`/`provider_message_id` on the row before or atomically with the send so a retry cannot double-send; AI calls that write results use an upsert keyed on input hash. Retry loops (`p-retry`, hand-rolled `for` with backoff) must cap attempts and only retry on 429/5xx/network, never on 4xx.
  FAIL PATTERN: server action retried by a double-click; two Stripe customers for one user; two "Your policy is bound" emails.
- **INT-06 · 3 · Inbound webhooks: signature verified, idempotent, acknowledged fast.**
  VERIFY per webhook route: raw body read (`await req.text()`, not `req.json()`) → provider verify (`stripe.webhooks.constructEvent`, `svix` `Webhook.verify`, Resend/Twilio HMAC, Supabase `Authorization` secret for DB webhooks) → event id stored in a `webhook_events(id primary key, provider, received_at, processed_at)` table with `insert ... on conflict do nothing` before processing → return 2xx within the provider's window (Stripe 20 s) and push heavy work to a queue (Inngest, Trigger.dev, QStash, `after()` in Next 15, or a Supabase `pg_net`/cron job). `curl -s -X POST <productionUrl>/api/webhooks/stripe -d '{}' -o /dev/null -w "%{http_code}"` → 400, never 200/500. Handler must also tolerate out-of-order events (`invoice.paid` before `customer.subscription.created`).
  FAIL PATTERN: `const event = await req.json(); if (event.type === 'checkout.session.completed') { ...grant access... }` — anyone can POST themselves a paid plan.
- **INT-07 · 2 · Test/sandbox mode is separated from live by environment, not by code edits.**
  VERIFY: Vercel env scoping — `vercel env ls` (or MCP `filter_project_envs`) → `STRIPE_SECRET_KEY` has different values for Production vs Preview/Development, and Preview uses `sk_test_`; Twilio/RingCentral sandbox numbers, Resend test domain (`onboarding@resend.dev`) and OpenAI org/project ids likewise. Code must not branch on `if (process.env.NODE_ENV === 'production') key = LIVE` — `grep -rn "sk_live\|sk_test" --include=*.ts` → empty outside tests. Webhook endpoints registered separately for test and live (check `stripe listen` instructions in README and the dashboard if access is granted).
  FAIL PATTERN: preview deployments charge real cards because every environment shares one `STRIPE_SECRET_KEY`.
- **INT-08 · 1 · API versions are pinned.**
  VERIFY: `grep -rn "apiVersion" --include=*.ts` → Stripe client constructed with an explicit `apiVersion` matching the dashboard's webhook version; OpenAI/Anthropic model ids are explicit strings in one config (`MODEL = 'claude-...'`), not `latest`; Google APIs use `google.<api>('v3')`; raw `fetch` URLs include `/v1/`, `/v2/`. Floating versions = PARTIAL.
  FAIL PATTERN: `new Stripe(key)` with no version; webhook payload shape changed after a dashboard upgrade; `invoice.subscription` became `invoice.parent.subscription_details`.
- **INT-09 · 2 · Logging around integrations leaks neither secrets nor PII.**
  VERIFY: `grep -rnE "console\.(log|error|info)\([^)]*(req\.headers|body|payload|event|response|err\b)" --include=*.ts` in integration files → whole-object logging of webhook payloads (card last4, emails, addresses) or of error objects containing `Authorization` headers is a finding; `grep -rn "Authorization" --include=*.ts | grep -i "log"`. Prefer `{ provider, eventId, status, durationMs }`. Check Sentry/PostHog config for `beforeSend` scrubbing or `sendDefaultPii: false`. Reference Privacy for retention.
  FAIL PATTERN: `console.log('stripe event', JSON.stringify(event))` on every webhook — customer emails in Vercel logs for 30 days.
- **INT-10 · 1 · Rate limits are respected on the way out.**
  VERIFY: bulk loops over a provider (sending 500 emails, enriching 2,000 Apollo contacts, syncing HubSpot) use batching/concurrency limits (`p-limit`, `p-queue`, provider batch endpoints like Resend `batch.send`) and handle `429` + `Retry-After`; `grep -rnE "Promise\.all\(.*\.map\(.*(resend|stripe|openai|hubspot|apollo)" --include=*.ts` → unbounded fan-out. Cron/edge-function jobs must checkpoint progress so a 429 mid-run resumes rather than restarts.
  FAIL PATTERN: `await Promise.all(contacts.map(c => apollo.enrich(c)))` — 429 after 50, the rest silently rejected.
- **INT-11 · 2 · Each integration has a kill switch.**
  VERIFY: a feature flag or env toggle checked at the call site (`FEATURE_EMAIL_ENABLED`, Vercel Edge Config / `flags` SDK, a `settings` row), so a provider outage or runaway bill can be stopped without a deploy; the "off" path must degrade gracefully (queue, skip, or show "temporarily unavailable"). `grep -rnE "(ENABLE|DISABLE|FEATURE)_[A-Z_]*(EMAIL|SMS|AI|STRIPE|SYNC)" --include=*.ts .env.example` → one per money/message/AI integration. None = FAIL for AI and SMS (metered spend), PARTIAL otherwise.
  FAIL PATTERN: the only way to stop the OpenAI bill at 2 a.m. is to rotate the key and break prod.
- **INT-12 · 1 · Setup is documented per integration.**
  VERIFY: `.env.example` lists every var from the Inputs diff with a one-line comment (where to get it, test vs live); README/`docs/integrations.md` has per-provider steps: dashboard URL, webhook endpoint path + events to subscribe, `stripe listen --forward-to localhost:3000/api/webhooks/stripe` for local dev, required OAuth scopes for Google/HubSpot. Vars present in code but missing from `.env.example` = FAIL (a new dev cannot boot).
  FAIL PATTERN: 23 `process.env.*` references, 9 in `.env.example`.
- **INT-13 · 1 · SDK major versions match the code that uses them.**
  VERIFY: `pnpm outdated --long | grep -iE "stripe|openai|@anthropic|resend|twilio|googleapis|@supabase"` → majors behind; then spot-check 2 call sites per lagging SDK against the installed version's types (`pnpm tsc --noEmit` catches most). Watch for known breaks: Stripe v17+ `apiVersion` literal types, OpenAI v4→v5 `beta` namespace moves, `@supabase/auth-helpers-nextjs` (deprecated) still imported instead of `@supabase/ssr`. Reference Dependencies for CVE detail.
  FAIL PATTERN: `@supabase/auth-helpers-nextjs` and `@supabase/ssr` both installed; two cookie formats in production.
- **INT-14 · 2 · Integrations are mockable and mocked in tests.**
  VERIFY: `msw` handlers or `vi.mock('stripe')`/`vi.mock('resend')` present (`grep -rln "msw\|vi.mock('stripe')\|vi.mock('resend')\|vi.mock('openai')" --include=*.test.*`); webhook handlers have tests feeding a signed fixture (`stripe.webhooks.generateTestHeaderString`) and an unsigned one expecting 400; no test hits a live provider (`grep -rn "sk_test_\|api\.stripe\.com" --include=*.test.*` → only in MSW handler URLs). Provider clients built via a factory (`getStripe()`) so tests can inject — a module-level `export const stripe = new Stripe(...)` is a PARTIAL. Coverage of these tests is scored in Test Coverage; here it is whether mocking is *possible and present*.
  FAIL PATTERN: `stripe.webhooks.constructEvent` mocked to always return a valid event — the signature check is never tested.

## Scoring notes
- INT-02 (literal or client-exposed secret), INT-05 (non-idempotent money/message write), INT-06 (unverified or non-idempotent webhook), INT-07 (live keys in preview) failing → CRITICAL findings (grade cap D).
- Score per integration, then report the worst row as the check status; list the others in the evidence so a clean Stripe does not hide a sloppy Twilio.
- A project with no money, message, or AI integration marks INT-05/06/11 N/A with the reason; analytics-only projects usually score here on INT-02/09/12.
- INT-07 needs Vercel env access (`vercel env ls`, MCP `filter_project_envs`) or a user screenshot; READ of `.env.example` alone is INFERRED (50) because it cannot show which value is set where.
- "To raise confidence": Vercel env listing, production URL for the unsigned-webhook `curl`, Stripe/Resend dashboard webhook config (endpoint URL + API version), `pnpm outdated` network access, a run of the test suite with MSW enabled.
