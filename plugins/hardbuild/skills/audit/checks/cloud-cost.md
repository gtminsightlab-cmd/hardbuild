# Cloud Cost & Backend audit — checks

**Purpose:** Reduce hosting costs and improve backend performance — find the routes, queries, assets, crons, and API calls that burn Vercel and Supabase quota (or third-party tokens) without earning it, and the missing guard rails that let a bug become a bill.
**Scorecard row:** Cloud Cost & Backend (Hercules: "Hercules Cloud"; here Vercel + Supabase) · **Report:** `audits/cloud-cost.md` · **Overlaps:** Performance (user-facing latency — here only the cost side of the same routes), Database (indexes DB-05, `select *` — here egress impact), Integrations (INT-10/11 rate limits and kill switches — here the spend ceiling), Observability (alerting in general — here spend alerts only). Reference, don't repeat.

## Inputs to gather first
- Route inventory with rendering mode: `pnpm next build 2>&1 | sed -n '/Route (app)/,/^$/p'` → the `ƒ` (dynamic) vs `○`/`●` (static/ISR) table; count dynamic routes.
- Config: `next.config.*` (`images`, `experimental`, `headers()`), `vercel.json` (`crons`, `functions`, `regions`), `middleware.ts` `matcher`, every `export const runtime|dynamic|revalidate|maxDuration`.
- Supabase: MCP `get_project` (compute size, region), `list_edge_functions`, Storage bucket list (`select id, public, file_size_limit from storage.buckets`), `select count(*), sum(size) from storage.objects` via `execute_sql` (metadata size column: `(metadata->>'size')::bigint`).
- Dashboard access (ask the user once): Vercel → Usage (function invocations, GB-hours, image optimizations, bandwidth, edge requests); Supabase → Reports / Usage (egress, DB size, realtime connections, storage). Without it, every "how much" check is READ or INFERRED and says so.
- `.hardbuild.json → audit.productionUrl` for cache-header `curl`s.

## Checks
Format: `ID · weight · check · how to verify (strongest first) · typical failure`

- **COST-01 · 3 · Rendering mode is deliberate: static/ISR where possible, dynamic only where needed.**
  VERIFY: from the build table, every `ƒ` route must have a reason (reads cookies/auth, per-user data). Marketing, pricing, blog, docs, legal pages rendered dynamic = FAIL. `grep -rnE "export const dynamic = ['\"]force-dynamic['\"]|unstable_noStore\(|noStore\(|cookies\(\)|headers\(\)" --include=*.tsx --include=*.ts app/` → each hit on a public page is a finding; a `cookies()` call in the root `layout.tsx` makes the entire tree dynamic. Public data pages should use `revalidate = N` or `unstable_cache`/`"use cache"` with tags. If dashboard access: Vercel Usage → Function Invocations by route — the top 5 routes are where the money is; quote them.
  FAIL PATTERN: `createServerClient()` with `cookies()` in root layout to show the avatar; every landing-page hit is a serverless invocation plus a Supabase auth round-trip.
- **COST-02 · 3 · Hot server paths are cached and not N+1.**
  VERIFY: `grep -rn -B2 -A6 "\.map(async\|for await\|for (const .* of" --include=*.ts --include=*.tsx app lib | grep -n "await supabase\|await fetch"` → awaits inside loops over rows = N+1 (one invocation now takes 40 DB round-trips). Repeated identical reads per request (`getUser()` called in layout, page, and 3 components) should be wrapped in React `cache()`. Expensive aggregates (dashboard counts, reports) belong in a Postgres view/RPC or `unstable_cache` with `revalidate`, not computed in JS from a full table read. Confirm `fetch` to own APIs from server components is absent (double invocation). If `pg_stat_statements` is on: `select calls, mean_exec_time, left(query,100) from pg_stat_statements order by calls desc limit 10;` → a query with calls ≫ page views is the N+1.
  FAIL PATTERN: quotes list page: 1 query for quotes, then `await supabase.from('clients').select().eq('id', q.client_id)` per quote.
- **COST-03 · 2 · Function duration and memory are bounded.**
  VERIFY: `grep -rn "maxDuration" app/ vercel.json` → set on routes that call AI/email/PDF generation, and ≤ plan limit (Hobby 60 s, Pro 300 s with Fluid); default routes should not need > 10 s. `vercel.json` `functions.memory` only where profiling justified it. If dashboard: Usage → "GB-Hours" and the p95 duration per function; any route averaging > 5 s that is not a known long task = finding. Long work (PDF, bulk import, AI batch) should be in a Supabase Edge Function, queue (Inngest/Trigger.dev/QStash), or `after()`/`waitUntil`, not inline in a user request.
  FAIL PATTERN: `maxDuration = 300` on a webhook route "to be safe"; one stuck provider call holds a function for 5 minutes.
- **COST-04 · 2 · Edge vs serverless placement is right.**
  VERIFY: `grep -rn "export const runtime" app/ middleware.ts` → `edge` only for tiny latency-sensitive logic (redirects, geo, A/B, auth-cookie refresh); Edge functions calling Supabase with heavy queries pay cross-region latency and Edge Request units. Middleware `matcher` must exclude `_next/static`, `_next/image`, `favicon.ico`, images, and public marketing paths — `grep -n "matcher" middleware.ts` → quote it; a missing/greedy matcher means every asset request runs middleware (billed). Supabase region (`get_project.region`) should match the Vercel function region (`vercel.json` `regions` or project default `iad1`) — a `us-west` DB with `iad1` functions adds ~60 ms × every query.
  FAIL PATTERN: `matcher: ['/((?!api).*)']` — middleware runs for every image, font, and chunk on every page view.
- **COST-05 · 2 · Image optimization quota is used sanely.**
  VERIFY: `grep -rnE "<img\s" --include=*.tsx | wc -l` (raw `<img>` for large images = bandwidth, no caching benefit) vs `next/image` usage; `unoptimized` props (`grep -rn "unoptimized" --include=*.tsx next.config.*`) → global `images.unoptimized: true` is a cost/perf trade — acceptable only with an external CDN already resizing. `images.remotePatterns` must be narrow (no `hostname: '**'` → anyone can use your optimizer quota by URL); `images.minimumCacheTTL` ≥ 2678400 for immutable user uploads; `sizes` prop present on responsive images (missing `sizes` = optimizer generates every width). If dashboard: Usage → Image Optimization "source images"; user-generated images with unique URLs per view (e.g. signed Supabase Storage URLs with changing tokens) defeat the cache — use Supabase's own `render/image` transforms or a stable public path.
  FAIL PATTERN: `<Image src={supabase.storage...createSignedUrl(...)}>` — every page view is a new source image; optimization quota gone by mid-month.
- **COST-06 · 2 · Bandwidth: assets are cached, versioned, and not oversized.**
  VERIFY: `curl -sI <productionUrl>/_next/static/<chunk>` → `cache-control: public, max-age=31536000, immutable`; `curl -sI <productionUrl>/<public asset>` (files in `public/`) → Vercel default is `max-age=0, must-revalidate` — large unversioned files in `public/` (videos, PDFs, fonts, hero images) need a `headers()` rule or should move to Supabase Storage/Blob with a CDN TTL. `find public -size +500k -exec ls -lh {} \;` → list them. API routes returning large JSON (`select *` of wide tables, base64 images) count as bandwidth and function egress; `curl -so /dev/null -w "%{size_download}\n" <productionUrl>/api/<hot route>` for the top 3.
  FAIL PATTERN: 14 MB `public/demo.mp4` on the landing page, served fresh on every visit.
- **COST-07 · 2 · Crons are necessary, infrequent, and cheap.**
  VERIFY: READ `vercel.json` `crons[]` → each has a schedule justified in a comment/README; Hobby allows daily only, Pro per-minute — a `* * * * *` cron doing a Supabase poll is 43,200 invocations/month for one job; prefer Supabase `pg_cron` + `pg_net` (`select * from cron.job;`) for DB-only maintenance, or a DB webhook/trigger for event-driven work. Cron route must verify `CRON_SECRET` (`grep -rn "CRON_SECRET" app/api/cron`) or it is a public endpoint anyone can hammer (cost + Security). Each cron route's `maxDuration` and whether it checkpoints (COST-02) for resume.
  FAIL PATTERN: `"schedule": "*/5 * * * *"` to "check for new leads" against a table that gets 30 rows a day.
- **COST-08 · 3 · Supabase egress is controlled: narrow selects, paginated, no leaked realtime.**
  VERIFY: `grep -rnE "\.select\(\s*\)|\.select\(['\"]\*['\"]\)" --include=*.ts --include=*.tsx | wc -l` → each on a wide/large table (joins, `jsonb`, text blobs) is a finding (reference Database for the correctness side); `grep -rnE "\.from\([^)]+\)\.select\([^)]*\)(?!.*\.(range|limit)\()" -P --include=*.ts --include=*.tsx` → list queries without `.range()`/`.limit()` on tables that grow (submissions, events, logs). Realtime: `grep -rn "\.channel(\|\.subscribe(" --include=*.tsx` → every subscription has a matching `removeChannel`/`unsubscribe` in the effect cleanup, filters by tenant (`filter: 'org_id=eq.…'`), and is not opened in a layout that stays mounted forever. MCP: `select count(*) from pg_stat_activity where application_name ilike '%realtime%'`. If dashboard: Supabase Usage → Egress by day; a step change = the day the `select *` shipped.
  FAIL PATTERN: `supabase.from('submissions').select('*')` with a `payload jsonb` column of 200 KB each, no range, for a list that shows 3 columns.
- **COST-09 · 2 · Database compute matches load; connections pooled.**
  VERIFY: MCP `get_project` → compute add-on; `select count(*), state from pg_stat_activity group by state;` and `select max_conn from (select setting::int as max_conn from pg_settings where name='max_connections') s;` → idle connections near the limit = app connecting direct (port 5432) instead of the pooler (`:6543`, `pgbouncer=true`/Supavisor) from serverless. `grep -rn "DATABASE_URL\|DIRECT_URL\|5432\|6543" .env.example drizzle.config.* prisma/schema.prisma` → ORM at runtime must use the transaction pooler URL; direct URL only for migrations. Over-provisioned compute with < 10% CPU for a month (dashboard Reports) = downsize finding; under-provisioned (CPU pegged, `too many connections` in logs via MCP `query_logs`) = perf finding.
  FAIL PATTERN: Prisma on serverless with the direct `5432` URL; "remaining connection slots are reserved" after a traffic spike.
- **COST-10 · 1 · Storage has a lifecycle: no orphans, limits enforced.**
  VERIFY: `select b.id, b.public, b.file_size_limit, b.allowed_mime_types, count(o.id), pg_size_pretty(sum((o.metadata->>'size')::bigint)) from storage.buckets b left join storage.objects o on o.bucket_id=b.id group by 1,2,3,4;` → buckets without `file_size_limit`/`allowed_mime_types` = unbounded; orphan check: `select count(*) from storage.objects o where bucket_id='<bucket>' and not exists (select 1 from public.<table> t where t.file_path = o.name);` for each bucket the app references. Confirm a delete path: when the owning row is deleted, is the object removed (`grep -rn "storage.from(.*).remove" --include=*.ts`) or a cleanup cron exists. Image transforms (`/render/image/`) instead of storing multiple sizes.
  FAIL PATTERN: 3 years of `avatars/<uuid>.png` for users who replaced their avatar 6 times; each still stored.
- **COST-11 · 1 · Edge Functions are lean.**
  VERIFY: `ls supabase/functions/*/` → each `index.ts`; `grep -rn "^import" supabase/functions/*/index.ts | grep -vE "jsr:|npm:|https://deno.land|https://esm.sh" ` for pinned imports; bundle size via `supabase functions deploy --dry-run` or `deno info`; functions importing `npm:@supabase/supabase-js` plus `npm:stripe` plus a PDF library in one function pay cold start on every invocation — split or move heavy work to a Vercel route with `after()`. Secrets via `Deno.env.get` only (MCP `create_edge_function_secret` list). N/A if no Edge Functions.
  FAIL PATTERN: one 4 MB function handling 6 unrelated webhooks; 1.8 s cold start on each.
- **COST-12 · 2 · Logging volume is production-grade.**
  VERIFY: `grep -rnE "console\.(log|debug|info)\(" --include=*.ts --include=*.tsx app lib | grep -v test | wc -l` → per-request logs in hot paths (middleware, layout, list queries) multiply by traffic; Vercel log retention and drains (MCP `list_drains`) are billed by volume. Expect a logger with levels (`pino`, `@vercel/otel`, `logtail`) and `LOG_LEVEL` set to `info`/`warn` in Production env; `grep -rn "console.log" middleware.ts` → any hit = finding. Supabase: `select * from pg_settings where name in ('log_min_duration_statement','log_statement')` — `log_statement='all'` on prod = finding.
  FAIL PATTERN: `console.log('session', session)` in middleware — one log line (with a JWT) per asset request.
- **COST-13 · 3 · Third-party metered spend is capped per user and globally.**
  VERIFY: for OpenAI/Anthropic/Twilio/Resend/Apollo calls (from Integrations inventory): `max_tokens`/`max_output_tokens` set explicitly (`grep -rn "max_tokens\|maxTokens\|max_output_tokens" --include=*.ts`); input truncated/validated for length before the call (a 2 MB paste = a $4 request); a per-user/per-org counter or rate limit (`@upstash/ratelimit`, a `usage` table with a daily cap) enforced before the call, not just displayed after; a global kill switch (Integrations INT-11); provider-side hard limits set (OpenAI/Anthropic monthly budget, Twilio spend alert — needs user confirmation or screenshot). Streaming endpoints must abort on client disconnect (`req.signal`). Any unauthenticated route that reaches an AI/SMS provider = FAIL regardless of caps.
  FAIL PATTERN: `/api/chat` with `maxDuration = 60`, no `max_tokens`, no rate limit, callable without login; a script loops it overnight.
- **COST-14 · 2 · Preview deployments and branches do not multiply cost.**
  VERIFY: Supabase Branching (MCP `list_branches`) → each preview branch is a billed compute instance; stale branches (> 7 days, PR merged/closed) = finding; `supabase/config.toml` `[remotes]`/branching settings; if not using Branching, confirm previews point at a shared dev project, never production (Integrations INT-07, `vercel env ls` → `SUPABASE_URL` Preview value). Vercel: `git.deploymentEnabled` in `vercel.json` to skip previews for bot/docs branches, `ignoreCommand` for unchanged apps in a monorepo; crons do not run on previews (default) — confirm no preview triggers prod webhooks.
  FAIL PATTERN: 11 Supabase preview branches alive for PRs closed in August.
- **COST-15 · 2 · Spend is observable: alerts exist and someone receives them.**
  VERIFY (requires dashboard/MCP access): Vercel → Settings → Billing → Spend Management: a spend limit or notification threshold set, Pro plan (Hobby has no alerts and no commercial use); Supabase → Organization → Billing → Spend Cap on (for predictable bills) or cost-control alerts; third-party provider budgets (COST-13). MCP `list_billing_charges`/usage endpoints if available — quote the current month. Without access → UNCHECKED, FAIL by rule; name it as the first confidence raiser.
  FAIL PATTERN: Supabase Spend Cap off "so prod never pauses", no alert; egress spike noticed on the invoice.

## Scoring notes
- COST-13 (uncapped metered AI/SMS spend, especially unauthenticated) and COST-08 (unbounded egress on a growing table) failing → CRITICAL (grade cap D) — they are the two ways a Vercel+Supabase app produces a surprise four-figure invoice. COST-01 failing on the public marketing surface → HIGH, CRITICAL only if it also pushes auth round-trips onto every anonymous hit.
- Mark a check VERIFIED only when you read the Vercel Usage / Supabase Reports page, ran the SQL, or `curl`ed the production header; config-only evidence is READ (85) and build-table evidence without traffic data is INFERRED (50) for the "drivers" checks (COST-01/02/03).
- Hobby/Free tiers: COST-15 is FAIL for a commercial app (no alerts, and the Vercel Hobby terms forbid commercial use); note it once and reference Legal.
- Pair every HIGH here with a dollar estimate or a unit count (invocations/month, GB egress) so the fix can be prioritized; a cost finding without a magnitude is MEDIUM at most.
- "To raise confidence": user grants Vercel Usage + Supabase Reports access (or screenshots of the current month), Supabase MCP (`get_project`, `list_branches`, `execute_sql` on `pg_stat_activity`, `storage.objects`), Vercel MCP (`filter_project_envs`, `list_drains`, `list_billing_charges`), `pg_stat_statements` enabled, production URL for cache-header `curl`s, a `pnpm next build` run for the route table.
