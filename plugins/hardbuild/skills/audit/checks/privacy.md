# Privacy audit — checks

**Purpose:** Review how data is collected, stored, and disclosed — know every column of personal data, keep only what is used, protect the sensitive ones, honour export and deletion, and make sure what the privacy policy says is exactly what the code and the vendors do.
**Scorecard row:** Privacy · **Report:** `audits/privacy.md` · **Overlaps:** Security (exposure vectors SEC-01/10/12), Identity & Access (RLS/tenant-isolation detail), Legal (policy pages, consent records, CAN-SPAM/TCPA), Database (schema hygiene), Observability (log pipeline). Reference, don't repeat.

## Inputs to gather first
- Schema: `supabase/migrations/*.sql`, or live via Supabase MCP `execute_sql`: `select table_name, column_name, data_type from information_schema.columns where table_schema='public' order by 1,2;`.
- Privacy policy text (`app/privacy/page.tsx` or MDX) — every behavioural sentence is a claim to trace.
- Vendors in code: `grep -rhoiE "(posthog|mixpanel|segment|gtag|googletagmanager|hotjar|clarity|intercom|crisp|sentry|resend|postmark|sendgrid|twilio|openai|anthropic|stripe|@vercel/analytics|@vercel/speed-insights)" app src components package.json --include=*.ts --include=*.tsx --include=package.json | sort -u`.
- `.hardbuild.json → audit.targetMarkets`, `audit.euUsers`, `audit.supabaseRegion`, `audit.aiFeatures`.

## Checks
Format: `ID · weight · check · how to verify (strongest first) · typical failure`

- **PRV-01 · 3 · Data inventory: every table/column holding PII is listed and sensitive ones flagged.**
  VERIFY (SQL): `select table_name, column_name, data_type from information_schema.columns where table_schema='public' and column_name ~* '(name|email|phone|mobile|ssn|tax_?id|ein|fein|dob|birth|address|street|zip|ip_?addr|payroll|wage|salary|claim|injury|diagnos|medical|health|license|dl_|bank|routing|account_?no)' order by 1,2;` → paste the result into the report as the inventory. Mark **sensitive**: SSN/EIN/FEIN, DOB, payroll/wages, claims/injury/medical (HIPAA-adjacent even for a non-covered entity), driver's licence, bank details. Else READ migrations with the same regex (`grep -rnoiE "<regex>" supabase/migrations`). Open the writers of every `jsonb` column (`data_type='jsonb'`) to see what actually lands there.
  FAIL PATTERN: `employees.ssn text` in a table nobody remembered; `metadata jsonb` holding full census uploads.
- **PRV-02 · 2 · Minimisation: no PII collected or stored that is never read.**
  VERIFY: for each PII column from PRV-01: `grep -rn "<column>" app src supabase/functions --include=*.ts --include=*.tsx | grep -vE "insert|upsert|update\(" | wc -l` → 0 reads = write-only column = finding; signup/onboarding forms with fields that have no downstream use (`grep -rnE "name=\"(phone|dob|ssn|fein|company_size)\"" app components`). Raw uploads kept after use: `select count(*) from storage.objects where bucket_id in ('census','loss-runs') and created_at < now() - interval '90 days';`.
  FAIL PATTERN: collecting full SSN for a WC indication that only needs class code, state and payroll.
- **PRV-03 · 3 · Encryption at rest for highly sensitive fields; TLS everywhere.**
  VERIFY (SQL): `select extname from pg_extension where extname in ('pgsodium','supabase_vault','pgcrypto');` and for every sensitive column from PRV-01: type is `bytea`/encrypted via pgsodium TCE (`select * from pg_seclabels where provider='pgsodium';`), lives in `vault.secrets`, or is app-encrypted (`grep -rnE "createCipheriv|libsodium|@noble/ciphers|encryptField\(" lib app src`) with the key in env, not repo. Plaintext `ssn text`/`bank_account text` = FAIL even with RLS. TLS: `curl -sI http://<productionUrl>` → 301/308 to https; `grep -rnE "fetch\(['\"]http://" app src supabase/functions` → 0; DB connection strings carry `sslmode=require`. Supabase disk encryption is platform default — note as INFERRED, not a PASS driver.
  FAIL PATTERN: SSN readable by any role that passes RLS; masking done only in the UI (`***-**-1234`).
- **PRV-04 · 3 · Retention and deletion policy implemented, not just written.**
  VERIFY: policy states periods → find enforcement: `select jobname, schedule, command from cron.job;` (pg_cron) or `vercel.json` `crons` → `/api/cron/purge`; the job hard-deletes or anonymises rows past retention (soft-deleted > 30 days, inactive leads > 24 months, raw uploads > 90 days) **and** the matching `storage.objects`. `select count(*) from <table> where deleted_at < now() - interval '30 days';` → 0. Backups/PITR window is stated in the policy if > retention.
  FAIL PATTERN: "retained as long as necessary" with no job; rows soft-deleted in 2024 still present and still in exports.
- **PRV-05 · 3 · Export and deletion request path (CCPA/CPRA; GDPR if EU users).**
  VERIFY: `grep -rnE "auth\.admin\.deleteUser|deleteAccount|exportData|data-request|/account/delete" app src supabase/functions` → self-serve "Delete account" and "Download my data" in settings, or a documented flow (`privacy@` mailbox + `data_requests(received_at, kind, fulfilled_at)` table, 45-day CPRA SLA). Cascades: `select tc.table_name, rc.delete_rule from information_schema.referential_constraints rc join information_schema.table_constraints tc on tc.constraint_name=rc.constraint_name where tc.table_schema='public';` → `CASCADE` or explicit cleanup for every FK to the user/org; storage objects, Stripe customer (`customers.del` or documented retention for tax records) and analytics identities (`posthog.reset()` / person delete API) handled. B2B: the agency admin can delete its own employees'/insureds' records.
  FAIL PATTERN: `auth.admin.deleteUser` leaves `profiles`, uploads and PostHog persons behind; "email us" with no tracking.
- **PRV-06 · 2 · Consent for analytics/cookies: banner where required, choice respected, no tracking before consent.**
  VERIFY: if `euUsers` or a consent-law market (EU/UK; CA "Do Not Sell or Share" if any ad-tech): a consent component gates init (`grep -rnE "posthog\.init|gtag\('config'|opt_in_capturing|opt_out_capturing|consent" app components`) — scripts load only after `consent=granted`; first load with no cookie: `curl -s <productionUrl> | grep -cE "googletagmanager|clarity\.ms|hotjar"` → 0 for non-essential tags. en-US only with first-party product analytics and no ad-tech: PASS with a policy notice, `opt_out_capturing` honoured, and session replay masking all inputs (`maskAllInputs: true` / `mask_all_text`) so SSN and payroll fields are never recorded.
  FAIL PATTERN: banner that sets nothing — PostHog fires on load regardless; session replay capturing the census upload form.
- **PRV-07 · 3 · Third-party scripts inventory and payloads: no PII in analytics events.**
  VERIFY: `grep -rnE "capture\(|track\(|gtag\(|identify\(|logEvent\(" app src components --include=*.ts --include=*.tsx -A4 | grep -iE "email|phone|first_?name|last_?name|ssn|fein|dob|payroll|premium|address"` → PII in event properties = finding (`identify(userId, { email })` is tolerable only when the policy names the vendor and the field; `email` inside `capture()` properties is not); `person_profiles: 'identified_only'` set; no `$set` of names into GA. Browser: DevTools network filter `posthog|google-analytics|clarity`, read 3 request bodies on the quote flow. Also what embedded widgets receive (Intercom `user_hash`, Stripe `customer_email`).
  FAIL PATTERN: `posthog.capture('quote_created', { insured_name, fein, payroll })`.
- **PRV-08 · 2 · Logs free of PII and secrets.**
  VERIFY: `grep -rnE "console\.(log|error|warn|info)\(.*(email|phone|ssn|password|token|payroll|body|req\.json|formData|JSON\.stringify\((event|user|profile))" app src supabase/functions --include=*.ts --include=*.tsx` → each hit reviewed; Sentry `sendDefaultPii: false` and a `beforeSend` scrubber (`grep -rn "beforeSend\|sendDefaultPii" sentry.*.config.*`); Vercel runtime logs (MCP `get_runtime_logs`, last hour) piped through `grep -E "[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[a-z]{2,}|\b[0-9]{3}-[0-9]{2}-[0-9]{4}\b"` → 0 hits; log drains go to a vendor named in the policy.
  FAIL PATTERN: `console.log('webhook', JSON.stringify(event))` dumping full Stripe customer objects; `console.error(err, { user })`.
- **PRV-09 · 3 · Storage buckets private by default; access via signed URLs scoped to owner/tenant.**
  VERIFY (SQL): `select id, public, file_size_limit, allowed_mime_types from storage.buckets;` → `public=false` for anything holding documents, census, loss runs, ACORD forms (public only for marketing assets); `select policyname, cmd, qual from pg_policies where schemaname='storage';` → select policies restrict by `(storage.foldername(name))[1] = auth.uid()::text` or org id, never `true`; code uses `createSignedUrl(path, ≤3600)` not `getPublicUrl` for private buckets (`grep -rn "getPublicUrl\|createSignedUrl" app src`). Fetch a known private object URL unauthenticated → 400/403. Upload constraints detail is Security SEC-10.
  FAIL PATTERN: `loss-runs` bucket `public=true` because "the paths are random".
- **PRV-10 · 3 · RLS as the privacy boundary between tenants (headline; detail in Identity & Access).**
  VERIFY (SQL): `select c.relname, c.relrowsecurity, c.relforcerowsecurity from pg_class c join pg_namespace n on n.oid=c.relnamespace where n.nspname='public' and c.relkind='r';` → `true` for every PRV-01 table; `select tablename, policyname, cmd, qual from pg_policies where schemaname='public';` → every select policy on a PII table carries a tenant predicate (`org_id = (select org_id from profiles where id = auth.uid())`), not merely `auth.uid() is not null`. Views: `select c.relname, c.reloptions from pg_class c join pg_namespace n on n.oid=c.relnamespace where n.nspname='public' and c.relkind='v';` → `security_invoker=on` on any view over PII, since views bypass RLS otherwise.
  FAIL PATTERN: `employees` has RLS but `employees_view` lacks `security_invoker` and exposes every tenant.
- **PRV-11 · 2 · Subprocessor/vendor list in the policy matches integrations actually used (claim-vs-code).**
  VERIFY: build the vendor list from Inputs (code + `package.json` + `vercel.json` + Supabase integrations + Edge Function secrets `supabase secrets list`) and diff against the policy's "service providers / third parties" section; every vendor receiving personal data (Supabase, Vercel, Stripe, Resend/Postmark, PostHog, Sentry, OpenAI/Anthropic, Twilio, CRM syncs) is named or covered by category with purpose. Vendors in the policy but absent from code are stale (MEDIUM); vendors in code but absent from the policy are the finding (HIGH).
  FAIL PATTERN: policy still lists Google Analytics (removed last year) and omits PostHog, Sentry and OpenAI.
- **PRV-12 · 1 · Small-print disclosures: email tracking, children's data, breach contact and runbook.**
  VERIFY: email tracking — `grep -rnE "track(Opens|Links|_opens|_links)|open_tracking|click_tracking" app src supabase/functions` and provider domain settings → off for auth/billing mail, on for marketing only if the policy says so (click-rewriting also breaks magic links behind corporate scanners). Children — policy has a "not directed to children under 13; we do not knowingly collect" clause. Breach — `ls docs/runbooks/*breach* docs/security/incident* SECURITY.md` names who is paged, the notification clocks (GDPR 72h; TX 60 days; CA "without unreasonable delay"), and `security@`/`privacy@` mailboxes that resolve (`dig MX <domain> +short`) and appear on the policy page (`grep -oE "(privacy|security|dpo)@[a-z0-9.-]+" app/privacy/page.tsx`).
  FAIL PATTERN: tracking pixels in password-reset mail; no contact beyond a marketing form; no runbook.
- **PRV-13 · 2 · Data residency matches policy statements.**
  VERIFY: Supabase MCP `get_project` → `region` (e.g. `us-east-1`); Vercel function regions (`vercel.json` `regions` or project settings); backups/PITR in the same region; compare to the policy ("stored in the United States"). AI and email vendors' processing regions are covered by the policy or by a transfer clause. If GDPR language is used with EU users, the transfer mechanism (SCCs/DPF) is named — otherwise the claim is a finding (→ Legal).
  FAIL PATTERN: policy promises "data never leaves the US" while the project sits in `eu-central-1` because that was the creation default.
- **PRV-14 · 2 · AI features: no training on customer data without disclosure; prompts carry only the PII the task needs (N/A if no AI).**
  VERIFY: `grep -rlE "openai|anthropic|@ai-sdk|generateText|streamText|chat\.completions" app src supabase/functions` → for each call site, READ the prompt assembly (`grep -n -B25 "messages:" <file>`): SSN, DOB, full names, contact details stripped or pseudonymised via a `redact()` helper unless the task needs them; no `store: true`/vendor-side logging without disclosure; policy has an AI section naming the vendor and stating inputs are not used for training (`grep -ciE "artificial intelligence|machine learning|model training|\bAI\b" app/privacy/page.tsx` ≥ 1). AI-generated quote text carries the human-review/indication disclaimer (→ Legal LGL-09).
  FAIL PATTERN: full ACORD 130 text, SSNs included, sent to a model to "summarise the submission"; policy silent on AI.

## Scoring notes
- PRV-01 (no inventory possible), 03 (plaintext SSN/bank), 04 (no enforced retention on sensitive data), 05 (no deletion path), 07 (PII in analytics), 09 (public bucket with documents), 10 (cross-tenant read) failing → CRITICAL. PRV-06/11/13 claim-vs-code mismatches → HIGH (regulatory misstatement). PRV-02/08/12 → MEDIUM unless the leaked field is sensitive, then HIGH.
- PRV-01 is the backbone: without the inventory every later check is INFERRED at best — cap area confidence at 50 and say so.
- Claim-vs-code: treat the privacy policy as a spec. Every behavioural sentence ("we encrypt", "we delete within 30 days", "we never sell") is traced to code or becomes a finding here with a note in Legal.
- "To raise confidence": Supabase MCP (`execute_sql`, `get_project`, `list_extensions`) for PRV-01/03/04/05/09/10/13; Vercel runtime logs for PRV-08; a browser session with network capture on the quote flow for PRV-06/07; provider dashboards (Resend/Postmark, PostHog, Sentry) for PRV-07/08/12.
