# Scalability & Reliability audit — checks

**Purpose:** Check that your app can handle a sudden surge in usage — a launch post, a partner sending 500 agents at once, a cron that fans out — without exhausting Postgres connections, timing out serverless functions, melting a third-party quota, or losing data. And that when something does break, you find out and can recover.
**Scorecard row:** Scalability & Reliability · **Report:** `audits/scalability.md` · **Overlaps:** Database (index design, query plans — SCL-04 only headlines it), Performance (page speed, bundle size, Core Web Vitals), Error Handling (per-call error paths — here only the *degradation* strategy), Security (rate limits as abuse control — here as DB protection), Dependencies (vendor lock). Reference, don't repeat.

## Inputs to gather first
- Runtime surface: `find app -name "route.ts" -o -name "actions.ts" | sort`; `ls supabase/functions/ 2>/dev/null`; `cat vercel.json 2>/dev/null` (crons, functions config); `git grep -nE "export const (runtime|maxDuration|dynamic|revalidate|preferredRegion)" -- 'app/**'`.
- Data access: `git grep -nE "createClient|createServerClient|createBrowserClient|postgres\(|new Pool\(|drizzle\(|PrismaClient" -- '*.ts' '*.tsx' | grep -v node_modules` and `grep -nE "DATABASE_URL|SUPABASE_DB_URL|POSTGRES_URL" .env.example .env.local 2>/dev/null | sed 's/=.*//'` (names only, never values).
- Third parties called from the server: `git grep -nohE "https://[a-z0-9.-]+\.(com|io|ai|dev)" -- 'app/**' 'lib/**' 'supabase/functions/**' | sort -u`.
- Supabase project tier and settings (MCP `get_project` if available) — Free/Pro, compute size, PITR add-on, region vs Vercel region.
- `.hardbuild.json → audit.productionUrl` for health and header checks.

## Checks
Format: `ID · weight · check · how to verify (strongest first) · typical failure`

- **SCL-01 · 2 · Serverless/edge function limits are set deliberately.**
  VERIFY: `git grep -nE "export const maxDuration" -- 'app/**/route.ts' 'app/**/actions.ts' 'app/**/page.tsx'` → every route that calls an LLM, generates a PDF, sends batch email or imports a file must declare `maxDuration` (Hobby cap 60s, Pro 300s with Fluid; default is 10–15s and silently kills the request). `jq '.functions' vercel.json` for memory. Routes doing heavy work on `runtime = 'edge'` (`git grep -nE "runtime = ['\"]edge" -- 'app/**'`) have a 25s initial-response limit and no Node APIs — flag any edge route that also imports `@supabase/supabase-js` with service role or does file processing.
  FAIL PATTERN: an AI summarization route with no `maxDuration`, failing at exactly 10s under load with a `FUNCTION_INVOCATION_TIMEOUT` nobody catches.
- **SCL-02 · 3 · Database connections go through the pooler (Supavisor, port 6543, transaction mode) from serverless.**
  VERIFY: for every direct Postgres connection found in Inputs (Drizzle/Prisma/`postgres.js`/`pg`), the URL must be the pooler: `grep -nE "pooler\.supabase\.com:6543|pgbouncer=true|\?pool" .env.example` and, for Prisma, `directUrl` only for migrations. Client must disable prepared statements in transaction mode (`postgres(url, { prepare: false })`, Prisma `?pgbouncer=true`). `@supabase/supabase-js` over PostgREST is fine (HTTP, no connection held) — but check it is instantiated per request, not cached in a module-level singleton on the server with a user session (`git grep -nE "^(export )?const supabase = create(Server)?Client" -- 'lib/**' 'app/**'` → module-scope server client with cookies is a bug, not just a scale problem). Check Vercel region matches Supabase region (`jq .regions vercel.json`, `git grep -n preferredRegion`; MCP `get_project` → region).
  FAIL PATTERN: `DATABASE_URL=postgres://...db.<ref>.supabase.co:5432/postgres` used by Drizzle in route handlers → 60 concurrent lambdas exhaust the direct connection limit and every request fails with `remaining connection slots are reserved`.
- **SCL-03 · 3 · No unbounded queries or N+1 loops on request paths.**
  VERIFY: `git grep -nE "\.select\(['\"]\*['\"]\)|\.select\(\)" -- '*.ts' '*.tsx' | grep -vE "\.(single|maybeSingle|limit|range)\(" ` → each `select` on a list table without `.limit()`/`.range()` is a finding (PostgREST default max-rows is 1000 unless changed — still a 1000-row payload per request); `git grep -nE "for \(.*of .*\)|\.map\(async|Promise\.all\(.*\.map" -- 'app/**' 'lib/**' | xargs -I{} echo {} | head` then open each and look for `await supabase.from(` inside the loop body → N+1; prefer `.in('id', ids)` or a joined `select('*, children(*)')`. Pagination on every list UI: `git grep -nE "\.range\(|cursor|pageSize|searchParams\.get\(['\"]page" -- 'app/**' | wc -l` vs. number of list pages.
  FAIL PATTERN: `const { data: orgs } = await supabase.from('orgs').select('*'); for (const o of orgs) { await supabase.from('members').select('*').eq('org_id', o.id) }` on the admin dashboard.
- **SCL-04 · 2 · Hot queries are indexed (headline only).**
  VERIFY: Supabase MCP `get_advisors` type `performance` → zero "unindexed foreign key" / "slow query" items; or `select schemaname, relname, seq_scan, idx_scan, n_live_tup from pg_stat_user_tables where seq_scan > idx_scan and n_live_tup > 5000 order by seq_scan desc;` → empty. Else READ: for each `.eq('col'` / `.order('col'` on large tables in request paths, `grep -rn "create index" supabase/migrations | grep col`. Full index design lives in Database.
  FAIL PATTERN: `.eq('org_id', ...)` on every tenant query with no index on `org_id`.
- **SCL-05 · 2 · Caching, ISR and CDN are used where data allows.**
  VERIFY: `git grep -nE "export const dynamic = ['\"]force-dynamic|cache: ['\"]no-store|noStore\(\)|cookies\(\)" -- 'app/**/page.tsx' | wc -l` vs. total pages → marketing, docs, pricing and public listing pages should be static or ISR (`export const revalidate = N`, `unstable_cache`/`"use cache"`, `revalidateTag`); `curl -sI <productionUrl>/ | grep -iE "x-vercel-cache|cache-control|age:"` → `HIT`/`STALE` on public pages, `MISS`/`private` on dashboards is correct. `next.config.*` `images` configured for remote Supabase Storage hosts (`remotePatterns`) so images go through the Vercel image CDN. Any expensive derived data (counts, aggregates, LLM output) recomputed per request without cache is a finding.
  FAIL PATTERN: `cookies()` called in the root layout, making the entire site dynamic including the landing page.
- **SCL-06 · 3 · Background work is off the request path.**
  VERIFY: inventory slow side effects — `git grep -nE "resend\.|sendgrid|openai\.|anthropic\.|stripe\.|puppeteer|pdf|fetch\(['\"]https" -- 'app/**/route.ts' 'app/**/actions.ts'` → for each, is it awaited inline before the response? Acceptable patterns: Vercel Cron (`jq .crons vercel.json`), Supabase `pg_cron` + `pg_net` (`grep -rn "cron.schedule\|net.http_post" supabase/migrations`), Supabase Queues (`pgmq`), Inngest/Trigger.dev/QStash, Edge Functions invoked from DB webhooks, Next `after()`/`waitUntil`. Fan-out (send to N users) must be a job, never a loop inside one request. Cron routes must verify `CRON_SECRET` (`git grep -n CRON_SECRET app/`).
  FAIL PATTERN: the "invite team" action loops over 200 emails with `await resend.emails.send` inside the server action; times out at 60s, half the invites sent, no record of which.
- **SCL-07 · 2 · Retried jobs and webhooks are idempotent.**
  VERIFY: each webhook route (Stripe, Supabase DB webhooks, Resend, Clerk) must persist the provider event id with a unique constraint before processing: `grep -rn "event_id\|stripe_event\|webhook_events" supabase/migrations | grep -i unique`; `git grep -nE "onConflict|upsert\(" -- 'app/api/**' 'supabase/functions/**'`. Cron jobs must be safe to run twice (`WHERE processed_at IS NULL ... FOR UPDATE SKIP LOCKED` or status column). Client-side money actions carry an idempotency key (`idempotencyKey` on Stripe calls). Signature verification itself is Security SEC-08.
  FAIL PATTERN: `checkout.session.completed` handler does `insert into subscriptions` — Stripe retries on a 500 and the user gets two rows and two welcome emails.
- **SCL-08 · 2 · Rate limits protect the database and paid APIs, not just the login form.**
  VERIFY: `git grep -nE "@upstash/ratelimit|Ratelimit|rateLimit\(|@vercel/firewall|checkRateLimit" -- 'app/**' 'lib/**' 'middleware.ts'` → applied to: AI/LLM routes, search/autocomplete, export/report generation, public read APIs, anything that calls a metered vendor. Vercel WAF rate-limit rules (MCP `get_firewall_config` or dashboard) count. Supabase side: PostgREST `max-rows` setting, statement timeout (`show statement_timeout;` via MCP → should be set for `authenticated`/`anon` roles: `alter role anon set statement_timeout = '8s'`). Abuse/auth rate limits live in Security.
  FAIL PATTERN: an unauthenticated `/api/search?q=` doing `ilike '%q%'` on a 2M-row table with no limit, no index, no statement timeout.
- **SCL-09 · 3 · Graceful degradation when a third party is down.**
  VERIFY: for each vendor in Inputs, open the call site: is there a timeout (`AbortSignal.timeout(ms)` on `fetch`, `timeout:` on the OpenAI/Stripe SDK), a fallback (cached result, queued retry, feature hidden), and does a vendor failure fail *only* the feature, not the page/action? `git grep -nE "AbortSignal\.timeout|signal:|timeout:" -- 'app/**' 'lib/**' | wc -l` vs. vendor call count. Check the critical path specifically: can a user sign in and see their data if the AI vendor, email vendor, or analytics vendor is unreachable? A circuit-breaker-ish guard (skip vendor for N minutes after M failures, stored in KV/Edge Config/DB) is a plus, not a requirement.
  FAIL PATTERN: the dashboard server component awaits an enrichment API with no timeout; when the vendor hangs, every dashboard load hits the Vercel function timeout and the whole app looks down.
- **SCL-10 · 1 · Health check endpoint exists and is monitored.**
  VERIFY: `ls app/api/health/route.ts app/api/healthz/route.ts 2>/dev/null` and `curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" <productionUrl>/api/health` → 200 in <1s; the handler should do a trivial DB round-trip (`select 1` via `supabase.rpc` or a 1-row read) and return `{ ok, db, version/commit }` without leaking config. Something must hit it: Vercel Checks, BetterStack/UptimeRobot/Checkly config, or a cron. No endpoint, or an endpoint nothing calls, = FAIL/PARTIAL.
  FAIL PATTERN: no health route; the first signal of a Supabase outage is a customer email.
- **SCL-11 · 3 · Observability: errors, logs and alerts reach a human.**
  VERIFY: `jq '.dependencies | keys | map(select(test("sentry|datadog|highlight|posthog|logtail|axiom|pino|opentelemetry")))' package.json`; Sentry: `ls sentry.*.config.ts instrumentation.ts` and `git grep -n "Sentry.init" ` → `dsn` set from env, `tracesSampleRate` > 0, `instrumentation.ts` registers server + edge. Vercel log drain configured (MCP `list_drains` → at least one) or a logging vendor receiving `console.*`. Alerts: a Sentry alert rule / Vercel notification / cron-failure alert that pages someone — READ the dashboard or ask; if the owner cannot name where an alert would arrive, FAIL. Supabase: `get_advisors` reviewed, log retention understood (7 days on Pro), DB webhooks or `pg_net` failures visible somewhere. Capture semantics (source maps, PII scrubbing) are Error Handling ERR-07.
  FAIL PATTERN: `@sentry/nextjs` installed, `SENTRY_DSN` never set in Vercel env, and no one has opened Vercel Logs since launch.
- **SCL-12 · 3 · Backups and point-in-time recovery are on and tested.**
  VERIFY: Supabase MCP `get_project` / dashboard → plan is Pro or above (Free has **no** backups), PITR add-on enabled for any project holding customer or billing data (daily backups alone mean up to 24h of loss), retention ≥7 days. Storage buckets: is there any backup of files (Supabase does not PITR Storage objects)? Look for a documented restore drill: `git grep -niE "restore|pitr|backup" -- '*.md' docs/`. Migrations are in git and reproducible (`ls supabase/migrations | wc -l` > 0; `supabase db diff` clean vs remote via MCP `list_migrations`).
  FAIL PATTERN: production on the Free tier with real policyholder data; one bad `delete` in a migration and it is gone.
- **SCL-13 · 2 · Stateless request handling — no in-memory state across requests.**
  VERIFY: `git grep -nE "^(export )?(const|let) \w+\s*(:\s*\w+(<[^>]+>)?)?\s*=\s*(new Map\(|new Set\(|\[\]|\{\}|0);?$" -- 'app/**/route.ts' 'app/**/actions.ts' 'lib/**' 'middleware.ts'` → module-level mutable collections used as caches, rate-limit counters, dedupe sets or job queues are findings (each Vercel instance has its own; they vanish on cold start). `global.__cache` / `globalThis.*` patterns likewise, except the sanctioned Prisma/Drizzle client singleton. File-system writes outside `/tmp` (`git grep -nE "fs\.(writeFile|mkdir|appendFile)" -- 'app/**' 'lib/**'`) are findings. Sessions must live in Supabase Auth cookies, never in memory.
  FAIL PATTERN: `const attempts = new Map<string, number>()` as the "rate limiter" for OTP verification.
- **SCL-14 · 1 · Cold-start weight is controlled.**
  VERIFY: `pnpm build 2>&1 | grep -A40 "Route (app)"` → look at the `First Load JS` and the `ƒ`/`○` markers; `ANALYZE=true pnpm build` with `@next/bundle-analyzer` if configured. Server-side: `git grep -nE "^import .* from ['\"](aws-sdk|@aws-sdk/client-s3|puppeteer|playwright|sharp|pdfkit|@react-pdf|openai|@anthropic-ai|lodash)['\"]" -- 'app/**' 'lib/**'` → heavy SDKs imported at module top in routes that rarely need them should be `await import()`-ed inside the handler; `next.config.*` `serverExternalPackages` for native deps; edge routes must not import Node-only libs. Vercel Fluid Compute enabled (MCP `get_project` → `fluid`/`resourceConfig`) reduces cold starts — note if off.
  FAIL PATTERN: `import puppeteer from 'puppeteer'` at the top of `lib/pdf.ts`, which is imported by the shared `lib/index.ts`, so every function cold-starts with a 60MB bundle.

## Scoring notes
- SCL-02 (direct DB connections from serverless), SCL-06 (fan-out inline), SCL-09 (vendor hang takes down the critical path), SCL-11 (no error capture reaching anyone) or SCL-12 (no backups/PITR on customer data) failing → CRITICAL (grade cap D). SCL-03 N+1 on the main dashboard → HIGH; SCL-07 non-idempotent payment webhook → CRITICAL and cross-reference Billing.
- Supabase MCP queries, `curl` against production and a completed `pnpm build` are VERIFIED (100). Reading `vercel.json`, env var *names*, and route code is READ (85). "Sentry is in package.json" is INFERRED (50) until the DSN and an actual captured event are confirmed.
- A project with no production URL and no Supabase MCP will land near 85 confidence at best — flag ⚠ and list exactly what access converts each UNCHECKED.
- "To raise confidence": Supabase MCP (`get_project`, `get_advisors`, `execute_sql` for `pg_stat_user_tables`, pooler settings); Vercel MCP or dashboard (`get_project` for Fluid/regions, `list_drains`, firewall rules, function config); a production URL for cache headers and the health endpoint; a read-only look at the Sentry/alerting project to confirm events arrive; a load probe (`npx autocannon -c 50 -d 20 <url>/api/<hot-route>`) run against a preview deployment with the owner's consent.
