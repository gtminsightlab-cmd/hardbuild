# Error Handling audit — checks

**Purpose:** Make sure errors are captured and handled gracefully. Every failure should (a) be noticed by the code, (b) be reported somewhere a human can see it, and (c) leave the user with a clear, honest, actionable screen instead of a spinner, a blank page, or a raw Postgres message.
**Scorecard row:** Error Handling · **Report:** `audits/error-handling.md` · **Overlaps:** Security (SEC-12 error responses leaking internals — here we check the *user-facing* and *capture* sides), Scalability & Reliability (SCL-09 degradation strategy, SCL-11 whether alerts reach a human), Accessibility (A11Y-09/14 how errors are *announced*), Privacy (PII in logs — headline only here), Test Coverage (tests for error paths). Reference, don't repeat.

## Inputs to gather first
- Call-site inventory: `git grep -nE "await supabase(\.\w+)*\.(from|rpc|auth|storage)" -- '*.ts' '*.tsx' | grep -v node_modules | wc -l` → total Supabase calls; `git grep -lE "\"use server\"|'use server'" -- 'app/**' 'lib/**'` → server-action files; `find app -name route.ts` → route handlers.
- Error UI files: `find app -name "error.tsx" -o -name "global-error.tsx" -o -name "not-found.tsx" -o -name "loading.tsx" | sort`; route groups: `find app -type d -name "(*)" | sort`.
- Capture tooling: `jq '.dependencies | keys | map(select(test("sentry|highlight|bugsnag|rollbar|datadog|posthog|pino|winston|logtail|axiom")))' package.json`; `ls sentry.*.config.ts instrumentation.ts instrumentation-client.ts 2>/dev/null`.
- Vendor fetches: `git grep -nE "await fetch\(" -- 'app/**' 'lib/**' 'supabase/functions/**' | wc -l`.

## Checks
Format: `ID · weight · check · how to verify (strongest first) · typical failure`

- **ERR-01 · 3 · Every Supabase call checks `error` (or throws it) before using `data`.**
  VERIFY: compare counts — `git grep -nE "await supabase(\.\w+)*\.(from|rpc|storage)" -- '*.ts' '*.tsx'` vs `git grep -nE "const \{ *data[^}]*error[^}]*\} *= *await supabase|\.throwOnError\(\)" -- '*.ts' '*.tsx'`; then find the misses precisely: `git grep -nE "const \{ *data *\} *= *await supabase|const \{ *data: *\w+ *\} *= *await supabase|await supabase\.from\([^)]*\)\.(insert|update|delete|upsert)\([^;]*\);?$" -- '*.ts' '*.tsx'` → each hit destructures `data` only or fires a write with no result read. For every `{ data, error }` destructure, open the file and confirm `error` is actually branched on within ~5 lines (`if (error)`), not just named. Also `supabase.auth.getUser()` — `user` can be `null` with no `error`; check `if (!user)` exists.
  FAIL PATTERN: `const { data } = await supabase.from('policies').select('*').eq('id', id); return data[0].premium;` — on an RLS denial `data` is `null`, the page throws `Cannot read properties of null`, and the user sees the generic error boundary with no clue they lack access.
- **ERR-02 · 3 · Route handlers wrap work in try/catch and return a typed error shape with the right status.**
  VERIFY: `for f in $(find app -name route.ts); do grep -q "try {" "$f" || echo "NO TRY: $f"; done`; `git grep -nE "NextResponse\.json\(\{ *error" -- 'app/**/route.ts' | grep -vE "status: *(4|5)[0-9]{2}" | head` → errors returned with 200 are findings; `git grep -nE "status: *500" -- 'app/**/route.ts'` → each 500 should be a true unexpected failure, not validation (400), auth (401), ownership (403) or missing (404). Look for one shared helper (`lib/api/response.ts`, `apiError(code, message, status)`) and a consistent body `{ error: { code, message } }` across all routes — mixed shapes (`{ error: string }` here, `{ message }` there) = PARTIAL. Zod failures must map to 400/422 with field paths.
  FAIL PATTERN: `catch (e) { return NextResponse.json({ error: e.message }, { status: 200 }) }` — the client's `res.ok` check passes and the UI shows success.
- **ERR-03 · 3 · Server actions return `{ error }` results; they do not throw to the client.**
  VERIFY: in each `"use server"` file, `grep -nE "^\s*throw " <file>` → a thrown error in a server action reaches the client as the opaque "An error occurred in the Server Components render" message in production (Next strips it). Expected shape: `type ActionResult<T> = { data: T; error: null } | { data: null; error: { code; message; fieldErrors? } }` returned from every exported action, consumed by `useActionState`/`useFormState` or a mutation hook that reads `.error`. `redirect()` throwing is fine (it is a control-flow throw) — but `redirect()` inside a `try` block is a classic bug: `git grep -nB5 "redirect(" -- 'app/**/actions.ts' | grep -E "try \{"` → each is a finding.
  FAIL PATTERN: `export async function createQuote(fd) { const parsed = schema.parse(fd); ... }` — a `ZodError` throws, the user gets a grey "Something went wrong" with no field highlighted.
- **ERR-04 · 3 · `error.tsx`, `global-error.tsx` and `not-found.tsx` exist where they matter.**
  VERIFY: `ls app/global-error.tsx app/not-found.tsx app/error.tsx 2>&1`; for each route group / top-level segment (`(marketing)`, `(auth)`, `(dashboard)`, `admin`): `ls app/<seg>/error.tsx app/<seg>/not-found.tsx 2>&1`. Open each `error.tsx`: must be `"use client"`, accept `{ error, reset }`, render a `reset()` button, show `error.digest` for support, and report to Sentry in a `useEffect` (`Sentry.captureException(error)`); `global-error.tsx` must render its own `<html><body>`. Dynamic routes (`[id]`) should call `notFound()` on a null row (`git grep -nE "notFound\(\)" -- 'app/**/\[*\]/**' | wc -l` vs. count of `[param]` pages). Loading states (`loading.tsx`/`Suspense`) prevent the "is it broken?" feeling — note absence as PARTIAL.
  FAIL PATTERN: one `app/error.tsx` only, so a failure in the dashboard sidebar unmounts the whole shell, including the nav the user needs to get out.
- **ERR-05 · 2 · React error boundaries isolate risky client trees.**
  VERIFY: `git grep -nE "ErrorBoundary|react-error-boundary|componentDidCatch" -- '*.tsx' | wc -l` → the widgets most likely to throw at runtime (charts over nullable data, rich-text editors, maps, third-party embeds, AI streaming output, PDF viewers) should each be wrapped so one failing card does not take out the page: list those components (`git grep -lE "recharts|react-pdf|@react-google-maps|mapbox|tiptap|lexical|useChat|useCompletion" -- '*.tsx'`) and check each is inside a boundary with a fallback that offers retry. Route-level `error.tsx` alone = PARTIAL.
  FAIL PATTERN: a `Recharts` tooltip formatter calls `.toFixed()` on `undefined` and the entire analytics page goes to the error screen.
- **ERR-06 · 3 · User-facing messages are actionable and never raw backend text.**
  VERIFY: `git grep -nE "toast(\.error)?\(\s*(error|err|e)(\.message)?\s*\)|\{error\.message\}|<p[^>]*>\{?\s*error\.message" -- '*.tsx' 'app/**/actions.ts'` → each shows Postgres/PostgREST/Auth text verbatim ("duplicate key value violates unique constraint \"profiles_email_key\"", "JSON object requested, multiple (or no) rows returned", "new row violates row-level security policy"). Expected: a mapping layer (`lib/errors.ts` with `toUserMessage(error)` keyed on `error.code` such as `23505`, `PGRST116`, `42501`, Supabase Auth `invalid_credentials`, `email_not_confirmed`) producing messages that say what happened **and** what to do next ("That email is already registered — sign in or reset your password"). Generic catch-all text must still offer a path (retry, contact, reference id). `console.error` as the only "handling" of a user-visible failure = FAIL.
  FAIL PATTERN: `toast.error(error.message)` after a Supabase insert surfaces `null value in column "org_id" violates not-null constraint` to a customer.
- **ERR-07 · 3 · Errors are captured server, client and edge, with source maps and context.**
  VERIFY: Sentry (or equivalent): `cat instrumentation.ts` → `register()` imports `sentry.server.config` and `sentry.edge.config` by `NEXT_RUNTIME`; `instrumentation-client.ts` or `sentry.client.config.ts` exists; `onRequestError` exported (`git grep -n "onRequestError" instrumentation.ts`) so server-component errors are captured; `next.config.*` wrapped in `withSentryConfig` with source-map upload (`SENTRY_AUTH_TOKEN` referenced in CI/Vercel env *names*; `widenClientFileUpload`, `hideSourceMaps`). `git grep -nE "Sentry\.(captureException|captureMessage)" -- 'app/**' 'lib/**' | wc -l` — the shared `apiError`/action-result helper should capture once centrally. Confirm one real event exists in the Sentry project (ask or dashboard) — otherwise INFERRED. Edge Functions in `supabase/functions/` need their own capture (`Sentry` Deno SDK or at least `console.error` + Supabase log retention) — check each `index.ts`.
  FAIL PATTERN: Sentry wired client-side only; every server action and route failure is invisible except in Vercel's 1-hour (Hobby) log window.
- **ERR-08 · 2 · Logs are structured and correlated; no PII in them.**
  VERIFY: `git grep -nE "console\.(log|error|warn)\(" -- 'app/**' 'lib/**' 'supabase/functions/**' | wc -l` vs. use of a structured logger (`pino`, `@logtail`, `next-axiom`, Sentry breadcrumbs). Correlation: a request id (`headers().get('x-vercel-id')` or generated `crypto.randomUUID()`) and the `user.id`/`org_id` attached to every log line and Sentry scope (`Sentry.setUser({ id })`, never `email` unless scrubbed). PII: `git grep -nE "console\.\w+\([^)]*(email|phone|ssn|password|token|card|address)" -- 'app/**' 'lib/**'` and `git grep -nE "console\.\w+\(.*(body|formData|req\.json|payload)\)" ` → dumping whole request bodies is a finding. Sentry `beforeSend`/`sendDefaultPii: false` set. Privacy owns the policy; here just the plumbing.
  FAIL PATTERN: `console.log('signup', body)` in the signup route — passwords and emails in Vercel logs forwarded to a third-party drain.
- **ERR-09 · 2 · No fire-and-forget promises without a catch.**
  VERIFY: `git grep -nE "^\s*void \w+(\.\w+)*\(" -- '*.ts' '*.tsx'` → each `void fn()` must be a function that catches internally — open and confirm; `git grep -nE "^\s*(supabase|fetch|resend|stripe|posthog|analytics)\.\w+.*\);\s*$" -- 'app/**' 'lib/**' | grep -v "await\|return\|\.then\|\.catch"` → un-awaited promise calls; `git grep -nE "\.then\([^)]*\)\s*;?\s*$" -- '*.ts' '*.tsx' | grep -v "\.catch"` → `.then` chains without `.catch`. In serverless, an un-awaited promise may also be killed when the response is sent — use `after()`/`waitUntil` (see Scalability). `process.on('unhandledRejection')` is not available on Vercel functions — the fix is at the call site. `useEffect(() => { loadData() }, [])` where `loadData` is async and uncaught is the client-side version: `git grep -nA2 "useEffect(() => {" -- '*.tsx' | grep -E "^\S+-\s+\w+\(\);?$" | head`.
  FAIL PATTERN: `void sendWelcomeEmail(user)` in the signup action — email vendor returns 429, nobody knows, 30% of new users never get the email.
- **ERR-10 · 2 · Form validation errors are shown inline, per field, with values preserved.**
  VERIFY: for each main form (`git grep -lE "useForm\(|useActionState|useFormState" -- '*.tsx'`): server-side zod `safeParse` → `error.flatten().fieldErrors` returned in the action result and rendered next to each field (`FormMessage`, or `aria-describedby`-linked `<p>`); the input must keep what the user typed (controlled form or `defaultValue` from returned values). Client-side `zodResolver` alone is PARTIAL — server validation must exist too (Security SEC-03 covers *that* it exists; here that its *output* reaches the field). Test in the browser: submit a bad email on sign-up → message beside the field, not a toast. Announcement semantics are A11Y-14.
  FAIL PATTERN: `if (!parsed.success) return { error: 'Invalid input' }` — 12 fields, no indication which one.
- **ERR-11 · 2 · Network failure and offline states are handled on the client.**
  VERIFY: data-fetching hooks (`@tanstack/react-query`, SWR, `useEffect`+fetch, Supabase realtime): `git grep -nE "isError|error:|onError|retry:" -- '*.tsx' | wc -l` vs. number of `useQuery`/`useSWR`/`fetch` call sites; each list/detail view needs an error state with Retry, distinct from empty and loading. Realtime: `supabase.channel(...).subscribe((status) =>` must handle `CHANNEL_ERROR`/`TIMED_OUT` (`git grep -nA3 "\.subscribe(" -- '*.tsx' | grep -c "CHANNEL_ERROR\|TIMED_OUT"`). Browser: DevTools → Network → Offline, then click the primary action — the UI must say so (toast or banner), not spin forever; `navigator.onLine`/`online`/`offline` listeners or react-query `networkMode` count. Mutations in flight when the tab closes: optimistic updates must roll back (`onError` in `useMutation`).
  FAIL PATTERN: the submit button stays in its `isPending` spinner forever after a network drop; the user reloads and loses the form.
- **ERR-12 · 2 · Transient third-party failures are retried with backoff — and only transient ones.**
  VERIFY: `git grep -nE "p-retry|async-retry|exponential-backoff|retry\(|maxRetries|backoff" -- 'app/**' 'lib/**' 'supabase/functions/**'` → vendor calls (OpenAI/Anthropic, Resend, Stripe, FMCSA/data APIs, webhooks you send) should retry on 429/5xx/`ECONNRESET` with jittered exponential backoff and a cap (3–5 attempts), respecting `Retry-After`; never retry 4xx validation errors, never retry non-idempotent writes without an idempotency key (SCL-07). SDK built-ins count (OpenAI `maxRetries`, Stripe `maxNetworkRetries`) — confirm they are set, not left at defaults that are 0 for some SDKs. Supabase-js does not retry PostgREST calls — wrap the critical reads that are allowed to retry.
  FAIL PATTERN: a hand-rolled `for (let i=0;i<10;i++)` loop with no delay hammering a rate-limited API, turning a 429 into a 10-minute ban.
- **ERR-13 · 2 · No empty or swallowing catch blocks.**
  VERIFY: `git grep -nE "catch\s*(\([^)]*\))?\s*\{\s*\}" -- '*.ts' '*.tsx'` → empty catches; `git grep -nA2 -E "catch\s*(\([^)]*\))?\s*\{" -- '*.ts' '*.tsx' | grep -E "^\S+-\s*(//|return null;?|return;?|return \[\];?|return false;?)\s*$" | head -30` → catches that only comment, or return a default without logging/capturing; `git grep -nE "catch \(\w+\) \{\s*console\.(log|error)\(\w+\);?\s*\}" ` → log-and-continue in a server action where the user then sees "success". Each must either rethrow, capture to Sentry and return a typed error, or have a comment explaining why ignoring is correct (e.g. best-effort analytics). Count: 0 PASS; ≤3 justified PARTIAL; more FAIL.
  FAIL PATTERN: `try { await supabase.from('audit_log').insert(...) } catch {}` — the compliance audit log silently stops writing after a schema change.
- **ERR-14 · 2 · Every outbound `fetch` and SDK call has a timeout.**
  VERIFY: `git grep -nE "await fetch\(" -- 'app/**' 'lib/**' 'supabase/functions/**' | wc -l` vs `git grep -nE "AbortSignal\.timeout\(|signal:\s*(controller|ac)\.signal|timeout:\s*[0-9]" -- 'app/**' 'lib/**' 'supabase/functions/**' | wc -l` → cite each fetch without a signal; SDKs: `new OpenAI({ timeout })`, `new Stripe(key, { timeout })`, `new Resend` (none — wrap it). Timeouts must be shorter than the function's `maxDuration` so the code, not the platform, decides what the user sees. Supabase client: `createClient(url, key, { global: { fetch: (u, o) => fetch(u, { ...o, signal: AbortSignal.timeout(8000) }) } })` for server use is the pattern to look for; absence on a heavy route is PARTIAL. On timeout, the user must get a specific message ("The carrier lookup is taking too long — try again"), not the platform's 504.
  FAIL PATTERN: `await fetch('https://api.vendor.com/enrich')` with no signal inside a server component → vendor hangs → Vercel 504 → `error.tsx` shows "Something went wrong" with nothing in Sentry because the function was killed, not thrown.

## Scoring notes
- ERR-01 (unchecked Supabase errors on a write path or a money/compliance read), ERR-02/03 (route or action failures reported as success or as an opaque production error), ERR-06 (raw Postgres/Auth text shown to customers — also leaks schema, cross-ref Security), or ERR-07 (no server-side capture at all) failing → CRITICAL (grade cap D).
- ERR-04 missing `error.tsx` on the main authenticated route group, ERR-09 fire-and-forget on a transactional email or billing side effect, ERR-13 empty catch around a write → HIGH.
- Grep counts (calls vs. checks, fetches vs. timeouts, catches vs. empty catches) are VERIFIED (100) for the *ratio*; the judgment that a specific site is unsafe is READ (85) once you have opened it and cited `file:line`. A Sentry package present with no visible event = INFERRED (50) at best. Browser checks (offline toggle, bad-form submit) are VERIFIED.
- Report the raw numbers (e.g. "148 Supabase calls, 97 check `error`, 51 misses — top 10 cited") so the next run shows movement.
- "To raise confidence": read access to the Sentry (or equivalent) project to confirm server/edge events and source maps resolve; a running dev server or preview URL to exercise offline, bad-input and 404 paths in the browser; Vercel runtime logs (MCP `get_runtime_errors`/`get_runtime_logs`) for the last 7 days to see which errors actually occur in production; a seeded test user to trigger RLS denials deliberately.
