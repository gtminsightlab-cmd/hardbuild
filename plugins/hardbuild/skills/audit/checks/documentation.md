# Documentation audit — checks

**Purpose:** Improve user-facing docs and help content — and the developer docs behind them — so a new user never has to guess what a field means, a new developer can run the app in 30 minutes, and nothing the docs promise has quietly stopped existing.
**Scorecard row:** Documentation · **Report:** `audits/documentation.md` · **Overlaps:** Copy & Content (microcopy tone), Error Handling (error-message plumbing), Build & CI (deploy pipeline itself), Product (claim-vs-code in nav/marketing), Security (secrets in `.env.example`). Reference, don't repeat.

## Inputs to gather first
- Doc inventory: `ls README* CHANGELOG* CONTRIBUTING* docs/ .github/ 2>/dev/null; find . -name '*.md' -not -path './node_modules/*' -not -path './.next/*' | head -50`.
- Env vars the code actually reads: `grep -rhoE "process\.env\.[A-Z0-9_]+" app src lib components middleware.ts supabase/functions 2>/dev/null | sort -u > /tmp/env-used.txt`; Edge Functions: `grep -rhoE "Deno\.env\.get\(['\"][A-Z0-9_]+" supabase/functions | sed "s/.*('//;s/.*(\"//" | sort -u >> /tmp/env-used.txt`.
- Env vars documented: `grep -oE "^[A-Z0-9_]+=" .env.example .env.local.example 2>/dev/null | tr -d = | sort -u > /tmp/env-doc.txt`.
- Public API surface: `find app -name route.ts | sed 's#/route.ts##;s#^app##'`; `ls supabase/functions`.
- In-app help surface: `grep -rn "<Tooltip\|<FormDescription\|<HoverCard\|aria-describedby\|helperText" app components --include=*.tsx | wc -l`.

## Checks
Format: `ID · weight · check · how to verify (strongest first) · typical failure`

- **DOC-01 · 3 · README setup actually works and its env vars match the code.**
  VERIFY: `comm -23 /tmp/env-used.txt /tmp/env-doc.txt` → vars the code reads but no example documents (each is a finding); `comm -13 ...` → documented vars nothing reads (debris). Then follow the README literally in a clean clone: `git clone <repo> /tmp/fresh && cd /tmp/fresh && cp .env.example .env.local && pnpm install && pnpm dev` — does it start without an undocumented step (Supabase CLI, `supabase start`, `supabase db push`, seed script, Stripe CLI)? READ the README for the package manager actually used (`ls pnpm-lock.yaml yarn.lock package-lock.json bun.lockb`) and Node version (`.nvmrc`/`engines`).
  FAIL PATTERN: README says `npm install` but repo has `pnpm-lock.yaml`; `SUPABASE_SERVICE_ROLE_KEY` read in code and absent from `.env.example`; README is still the `create-next-app` boilerplate.
- **DOC-02 · 3 · `.env.example` is complete, commented, and secret-free.**
  VERIFY: `test -f .env.example || echo MISSING`; every line has a comment or placeholder explaining *where to get it* (`grep -cE "^#|^[A-Z_]+=\s*(your_|<|xxx|changeme|$)" .env.example` vs line count); no real values: `grep -nE "=(sk_live_|sk_test_|eyJ[A-Za-z0-9_-]{20,}|https://[a-z]{20}\.supabase\.co)" .env.example` → must be empty (a real `eyJ…` anon key or project URL committed as "example" is a Security finding too). `NEXT_PUBLIC_` vs server-only grouping is visible.
  FAIL PATTERN: `.env.example` has 4 vars, code reads 11; real anon key and project URL committed "because they're public anyway"; no hint that `SUPABASE_SERVICE_ROLE_KEY` comes from Dashboard → Settings → API.
- **DOC-03 · 2 · In-app help on complex fields (tooltips, descriptions, examples).**
  VERIFY: list fields a new user cannot guess — anything with a domain term, a code, a format, a threshold, or a consequence (`grep -rnE "<(Form)?Label[^>]*>[^<]*(rate|code|class|limit|FEIN|EIN|NAICS|SIC|DOT|MC|API|webhook|slug|token|cron|threshold)" app components --include=*.tsx -i`). Each must have an adjacent `<FormDescription>`, `<Tooltip>`, placeholder *example* (`placeholder="e.g. 8810"`), or link to docs. Count: `grep -rn "<FormDescription\|<Tooltip" app components --include=*.tsx | wc -l` vs `grep -rn "<FormField\|<FormItem" app components --include=*.tsx | wc -l`.
  FAIL PATTERN: "Class code" field with no example or lookup; a toggle labelled "Auto-bind" with no explanation of what it binds; settings page of 12 switches and zero descriptions.
- **DOC-04 · 3 · Error messages tell the user what happened and what to do.**
  VERIFY: `grep -rnE "(toast|setError|message:|error:)\s*\(?['\"][^'\"]*['\"]" app components lib --include=*.ts* | grep -iE "something went wrong|an error occurred|error|failed|oops|try again" | grep -viE "because|please (check|enter|choose|select|contact)|must|required|already|invalid [a-z]" | head -30` → generic strings with no cause and no next step; `grep -rn "error.message" app components --include=*.tsx | head` → raw Supabase/Postgres messages (`duplicate key value violates unique constraint "…"`, `JWT expired`, `new row violates row-level security`) shown to end users are findings. READ `app/error.tsx`, `app/global-error.tsx`, `app/not-found.tsx` exist and offer a way back (retry button, home link, support link). Plumbing detail → Error Handling.
  FAIL PATTERN: `toast.error('Something went wrong')` on 30 call sites; `{error.message}` rendered straight from PostgREST; 404 page with no link anywhere.
- **DOC-05 · 1 · Changelog / release notes exist and are current.**
  VERIFY: `ls CHANGELOG.md docs/changelog* app/**/changelog* 2>/dev/null`; `head -20 CHANGELOG.md` → top entry within the last release (`git log -1 --format=%cd` vs top date; `git tag --sort=-v:refname | head -3`). Or in-app "What's new" (`grep -rn "whats-new\|changelog\|release-notes" app -il`). Or `.github/release.yml` / release-please / changesets (`ls .changeset 2>/dev/null`). N/A for pre-launch projects with no users, say so.
  FAIL PATTERN: `CHANGELOG.md` last touched 9 months ago while `git log` shows 200 commits since; version in `package.json` still `0.1.0` after launch.
- **DOC-06 · 2 · Public API endpoints and webhooks are documented.**
  VERIFY: for each `route.ts` reachable without a browser session (API keys, webhooks, public GET), a doc must state method, auth, request/response shape, and error codes: `ls docs/api* app/api/**/README.md openapi.* swagger.* 2>/dev/null`; `grep -rn "openapi\|swagger\|@hono/zod-openapi\|next-swagger-doc" package.json`. Cross-check: documented paths exist in the route inventory and vice-versa. Supabase Edge Functions (`ls supabase/functions`) each have a header comment or doc entry stating who calls them. N/A if every endpoint is first-party and session-only, say so.
  FAIL PATTERN: `/api/v1/quotes` consumed by a partner with the only "docs" being a Slack message; webhook handler accepts 6 event types, docs mention 2; OpenAPI file last regenerated before 3 schema changes.
- **DOC-07 · 3 · A new developer can run the app locally in under 30 minutes.**
  VERIFY: time the DOC-01 clean-clone run; list every step that required tribal knowledge (which Supabase project, how to get a user, how to seed data, how to run migrations: `ls supabase/seed.sql supabase/migrations | head`, `grep -n "\"db:\|\"seed\|\"supabase" package.json`). Required: prerequisites with versions, `supabase start` or hosted-project link, `supabase db reset`/`push`, seed, test login credentials or sign-up path, and "how to verify it works" (one URL + what you should see).
  FAIL PATTERN: works only on the founder's machine; migrations must be applied by hand in the SQL editor; no seed, so every screen is empty; `supabase/config.toml` references a project ref the new dev can't access.
- **DOC-08 · 3 · Runbook for deploy, rollback, and migrations.**
  VERIFY: `ls docs/runbook* docs/deploy* docs/operations* RUNBOOK.md DEPLOY.md 2>/dev/null`; `grep -rniE "rollback|revert|promote|instant rollback" docs README.md | head`; must cover: how a deploy happens (Vercel Git integration? `grep -n "vercel" .github/workflows/*.yml`), how migrations reach prod (`supabase db push` in CI? `grep -rn "supabase db push\|supabase migration up" .github/workflows/`), how to roll back a bad deploy (Vercel "Promote previous"/`vercel rollback`) *and* a bad migration (down migration or forward-fix policy — Supabase CLI has no down migrations; the runbook must say which), who has access, where logs live (Vercel runtime logs, Supabase `query_logs`), and env-var change procedure.
  FAIL PATTERN: no runbook; CI applies migrations before the code deploys with no compatibility note; rollback = "ask the founder"; secrets rotation undocumented.
- **DOC-09 · 2 · Architecture overview exists and matches the code.**
  VERIFY: `ls docs/architecture* ARCHITECTURE.md docs/adr 2>/dev/null`; the overview must name: route groups and what each is for (`ls -d app/*/`), where data access lives (`lib/supabase/*`, `lib/db/*`), auth flow (`middleware.ts` + `@supabase/ssr`), background work (Edge Functions, cron: `ls vercel.json` → `crons`, `supabase/functions`), third parties (Stripe, Resend, etc. from `package.json`). Cross-check each named component exists; cite stale ones. A single diagram (Mermaid in Markdown is fine) is worth more than ten pages.
  FAIL PATTERN: doc describes Prisma but repo uses Supabase client; mentions `pages/` router after the App Router migration; no mention of RLS as the authorization boundary.
- **DOC-10 · 2 · Support / contact path is visible to users.**
  VERIFY: `grep -rnE "mailto:|support@|help@|/support|/help|/contact|intercom|crisp|zendesk|tawk" app components --include=*.tsx -i | head` → must appear in the signed-in shell (footer/user menu), on `error.tsx`, and on `not-found.tsx`; the address must be real (`grep -rn "support@example.com\|hello@yourdomain" app components` → placeholder = FAIL). In browser: from the dashboard, how many clicks to reach a human?
  FAIL PATTERN: contact only on the marketing footer, invisible once logged in; error page says "contact support" with no link; `mailto:` to a domain that isn't the product's.
- **DOC-11 · 3 · Docs make no claims about features that no longer exist (claim-vs-code).**
  VERIFY: extract feature nouns and routes from README/docs/help pages: `grep -rhoE "\`?/[a-z][a-z0-9/_-]+\`?" README.md docs/**/*.md | tr -d '\`' | sort -u` → each path must exist in the route inventory (`test -f app$p/page.tsx` or a `route.ts`); `grep -rhoE "(npm|pnpm|yarn) (run )?[a-z:-]+" README.md docs | awk '{print $NF}' | sort -u` → each script exists in `package.json`; env var names in docs ⊆ `/tmp/env-used.txt`; UI labels quoted in help text ("click **Export CSV**") must appear in code (`grep -rn "Export CSV" app components`). Screenshots in `docs/` older than the last UI overhaul (`git log -1 --format=%cd -- docs/*.png`).
  FAIL PATTERN: README still documents `/admin/reports` removed two sprints ago; help center explains a "Team" tab that was renamed "Workspace"; docs reference `pnpm test:e2e` which no longer exists.
- **DOC-12 · 1 · Docs are discoverable from inside the product.**
  VERIFY: `grep -rnE "href=[\"'](/docs|https://docs\.|/help)" app components --include=*.tsx | wc -l` → link in user menu/sidebar footer; `?` icon or `Cmd+/` help shortcut; onboarding links to the relevant doc section rather than the docs root. N/A if there are no user-facing docs yet — then DOC-03 carries the weight.
  FAIL PATTERN: beautiful docs site with zero links from the app; docs link opens the marketing home page.
- **DOC-13 · 1 · Code-level docs where intent is non-obvious.**
  VERIFY: `grep -rn "^/\*\*" lib app/api supabase/functions --include=*.ts | wc -l` vs exported functions (`grep -rn "^export (async )?function\|^export const .* = (async )?(" lib --include=*.ts | wc -l`); every migration has a leading comment stating intent (`for f in supabase/migrations/*.sql; do head -3 "$f" | grep -q "^--" || echo "no comment: $f"; done`); every `.rpc()`/Postgres function has a `comment on function`. Prose-free is fine; intent-free is not.
  FAIL PATTERN: 40 migrations named `20240311_fix.sql` with no comments; a 200-line `calculatePremium()` with no description of inputs/units; `// TODO remove` from 2024.

## Scoring notes
- DOC-01 (setup fails or env vars missing), DOC-04 (raw DB errors to users or dead-end error pages), DOC-07, DOC-08 (no rollback/migration path written down), DOC-11 (docs promising removed features) → CRITICAL; grade cap D. A real secret in `.env.example` (DOC-02) is CRITICAL and is filed under Security as the primary finding, referenced here.
- DOC-05, DOC-06, DOC-12 are N/A when the stated condition holds (pre-launch, no public API, no docs site); say why in one clause rather than scoring them.
- DOC-01/07 are VERIFIED only by an actual clean-clone run (quote the first failing command). Reading the README and judging it plausible is INFERRED (50), not READ. DOC-11 is READ (85) when every doc path/script/env var was cross-checked by command and cited.
- "To raise confidence": a clean clone with network access for `pnpm install` and `supabase start` (Docker); a test login; `productionUrl` for DOC-10 and `error.tsx` behaviour; access to any external docs site or help center (URL in `.hardbuild.json → docs.url`); Vercel MCP to confirm the deploy/rollback flow the runbook describes is the one actually in use.
